Build and deploy

This page walks through the files elci build produces, how to protect your on-chain data layout from accidental changes, and how off-chain code loads the compiled script. The examples use the vesting contract from the vesting tutorial.

Building

Section titled “Building”

Each validator gets its own directory:

  • Directorybuild/
    • Directoryvalidators/
      • elci-outputs.json the files Elci owns, per validator
      • Directoryvesting/
        • validator.flat the script, FLAT-encoded UPLC
        • validator.plutus a Plutus V3 text envelope
        • validator.plutus.json the Julc artifact for off-chain code
        • abi.json the data layout of parameters, datums and redeemers
FileContentsUse it for
validator.flatThe raw UPLC program in FLAT encodingTools that read FLAT directly
validator.plutusA text envelope: type, description and cborHex, with the script bytes CBOR-wrapped twiceTools that read Plutus script envelopes
validator.plutus.jsonJulc’s validator artifact: cborHex, hash, params, purpose, sizeBytesLoading the script with Cardano Client Lib
abi.jsonHandlers, datum, redeemer and parameter schemas, constructor tags and field orderBuilding data off-chain; detecting layout changes

Neither validator.plutus.json nor abi.json is a CIP-57 blueprint; Elci doesn’t generate blueprints yet.

How a build writes files

Section titled “How a build writes files”
  • All or nothing. Every selected validator is compiled, and checked against its expected-abi, before any file is written. If one fails, nothing is published and the previous outputs stay as they were.
  • Selection. elci build . --validator vesting builds only the named validators (repeat the option for more) and leaves the others’ outputs alone.
  • Cleanup. A full build removes the outputs of validators you have deleted from elci.toml. It only removes files listed in elci-outputs.json, so anything else you put in those directories is kept.
  • Applied scripts. An applied.plutus.json written by elci apply is removed by the next build of its validator, because it was applied to the previous script.

The Julc artifact

Section titled “The Julc artifact”

validator.plutus.json is the file off-chain code loads (cborHex shortened):

FieldMeaning
typeAlways PlutusScriptV3
purposespending, minting, withdraw, certifying, voting or proposing for one handler; multi for several
descriptionThe validator’s name
cborHexThe script, CBOR-wrapped twice as Cardano Client Lib expects
hashThe script hash; empty while parameters are still to be applied
paramsThe parameters still to be applied, as name:type, comma-separated; records show as Record
sizeBytesThe size of the FLAT script

Script hashes

Section titled “Script hashes”

The script hash identifies a deployed script:

  • For a spending validator, the script address is built from it.
  • For a minting policy, it is the policy id.
  • For withdraw and certify, it is the stake credential.

A validator without parameters has its hash in validator.plutus.json. A parameterized validator has an empty hash until you apply its parameters with elci apply, which prints the hash and writes it into applied.plutus.json (see Parameterized validators). Any change to the source, the handlers, the parameters or the compiler version can change the hash, so record which build you deployed.

Before you deploy

Section titled “Before you deploy”

Elci is a development preview, and its output has not been audited. Deploy to a test network first, and treat any mainnet use as experimental. Before deploying a script:

  • Run elci test, with scenarios for every purpose and every way a transaction should be rejected.
  • Check the budgets your scenarios report. The ledger limits every transaction’s CPU and memory, and the fee grows with both.
  • Commit the ABI and set expected-abi, so that later changes can’t silently break existing datums.
  • Apply parameters with elci apply, which checks their shape, and double-check their meaning against abi.json.
  • Record the script hash you deployed.
