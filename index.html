Why Elci

The clarity of Elm for code that moves value.

On-chain code has no second chance. Elci gives you a small, predictable functional language, and a compiler that refuses programs it cannot represent faithfully rather than erasing types to raw data.

Familiar and functional

Elm syntax, pure functions, currying and pipelines. If you have written Elm, Haskell or F#, you can read an Elci contract on day one.

Types that catch mistakes

Hindley–Milner inference, exhaustive pattern matching and rejected unreachable branches. Errors quote your code, name what differs and suggest a fix.

Strict data boundaries

Datums, redeemers and parameters are decoded strictly from their types. Malformed data fails before your logic runs.

One script, every purpose

Named validators combine spend, mint, withdraw, certify, vote and propose handlers, with deployment parameters and ABI drift checks.

Testing built in

Unit tests, transaction scenarios on the deployed script, and property tests that shrink failures, all written in Elci.

Standing on Julc

Julc's PIR verifier, optimizer and UPLC pipeline, its standard library, typed Map, Array and Bytes, and a fast native CLI.

See it in action

From validator to property test, in one language.

Real code from the Elci examples. Each sample compiles, and every test passes.

src/Vesting.elm
module Vesting exposing (VestingAction(..), VestingDatum, validate)

import Interval
import Julc.Ledger exposing (PubKeyHash, ScriptContext)
import Tx


type alias VestingDatum =
    { beneficiary : PubKeyHash
    , deadline : Int
    }


type VestingAction
    = Claim


validate : VestingDatum -> VestingAction -> ScriptContext -> Bool
validate datum action ctx =
    case action of
        Claim ->
            Interval.isEntirelyAfter datum.deadline ctx.txInfo.validRange
                && Tx.signedBy datum.beneficiary ctx

A typed datum and redeemer, the validity range and the signatories. The datum and redeemer are strictly decoded from their types before validate runs.

tests/VestingTest.elm
claimFrom : Int -> Scenario
claimFrom time =
    Scenario.spend "vesting" (Scenario.outRef "vesting" 0) (Data.encode datum)
        |> Scenario.redeemer (Data.encode Claim)
        |> Scenario.validFrom time


claimsAfterTheDeadline : Scenario
claimsAfterTheDeadline =
    claimFrom 1001
        |> Scenario.signedBy beneficiary


claimsAtTheDeadlineFail : Scenario
claimsAtTheDeadlineFail =
    claimFrom 1000
        |> Scenario.signedBy beneficiary
        |> Scenario.expectFailure

A scenario is a transaction described as data. elci test compiles the validator exactly as elci build does and runs the deployed script in a complete ledger context.

tests/VestingTest.elm
{-| Whenever a signed claim's validity range starts, it succeeds exactly when that is
after the deadline.
-}
claimsSucceedExactlyAfterTheDeadline : Int -> Property
claimsSucceedExactlyAfterTheDeadline time =
    let
        signed =
            claimFrom time
                |> Scenario.signedBy beneficiary
    in
    if time > datum.deadline then
        Property.scenario signed

    else
        Property.scenario (Scenario.expectFailure signed)

A function returning a Property runs 100 times with generated arguments. A failure is shrunk to a small counterexample and reported with a reproducible seed.

elci.toml
[project]
source-directories = ["src"]
target = "plutus-v3-pv11-uplc-1.1.0"
julc-version = "0.1.0-pre20-ebaf028-SNAPSHOT"

# One script: the treasury address spends payouts and withdraws its staking rewards.
[validators.treasury]
boundary = "julc-strict-v1"
parameters = ["admin"]
spend = "Treasury.spend"
withdraw = "Treasury.withdraw"

# A separate script and policy id.
[validators.badge]
boundary = "julc-strict-v1"
parameters = ["admin"]
mint = "Badge.mint"

Configuration, not syntax, decides deployment. One validator can spend and withdraw with shared parameters, and another is a separate minting policy.

src/Example/Offer.elm
module Example.Offer exposing (validate)

import Julc.Ledger exposing (ScriptContext)
import Julc.Math as Math


validate : Int -> Int -> ScriptContext -> Bool
validate minimumAda offeredLovelace _ =
    Math.floorDiv offeredLovelace 1000000 >= minimumAda

How it works

Your language, Julc's backend.

Elci owns the language: parsing, modules, type inference and lowering to typed PIR. Julc owns the rest: verification, linking, optimization and UPLC. The two meet at a checked, revisioned contract.

  1. 01.elm sourceModules, types and handlers
  2. 02Parse & resolveModules, imports, Java exports
  3. 03Infer & checkHM types, exhaustive patterns
  4. 04Typed PIRSpecialized, strict lowering
  5. 05Julc backendVerify, link, optimize
  6. 06Plutus V3UPLC script + ABI
