Records and tuples

Records and tuples group several values into one. This page shows how to create, read, update and destructure them, and how Elci encodes them as on-chain data. That encoding matters as soon as a record becomes a datum or redeemer.

Records

Section titled “Records”

A record has named fields. type alias gives a record type a name:

  • { price = 2000, active = True } creates a record. It has type Listing because it has exactly those fields.
  • listing.price reads a field.
  • { listing | price = ... } is a record update: a copy of listing with new values for the named fields. You can update several fields at once, separated by commas. The record to update must be a plain name.

Records are values. An update creates a new record and leaves the original unchanged.

Record constructors

Section titled “Record constructors”

A record alias also defines a constructor function. Its arguments follow the order of the fields in the declaration:

Listing 2000 True is the record { price = 2000, active = True }. elci eval prints record fields in alphabetical order, which is a hint about how Elci stores them.

Accessor functions

Section titled “Accessor functions”

As in Elm, .amount is a function that reads the field amount of a record. It is short for \payout -> payout.amount, and it is handy with list functions:

A record that another module exposes is read the same way. Config.settings.fee reads the field fee of the value settings in module Config:

A qualified name is written without spaces and ends at its first lowercase part: Config.settings is the value, and .fee reads its field. In List.map .amount payouts, the space before .amount makes it an accessor passed to List.map.

How records are stored on-chain

Section titled “How records are stored on-chain”

Cardano stores datums and redeemers as Plutus Data: integers, byte strings, lists, maps and constructors (a tag number with a list of fields). Julc.Data.encode turns any value into its Data, so you can see exactly what goes on-chain:

  • A record is a constructor with tag 0.
  • Its fields are sorted alphabetically by name, whatever order you declared them in. That is why active (True, itself encoded as constructor 1 with no fields) comes before price (2000).

This has practical consequences for datums and redeemers:

  • Reordering the fields of a record declaration doesn’t change its encoding.
  • Renaming a field can change the encoding, because it can change the sort order. Data already on-chain would no longer decode. The build’s abi.json records the exact layout, so you can detect such changes.

Datums and redeemers covers the encoding rules for every type.

Tuples

Section titled “Tuples”

A tuple groups two or three values without naming them: ( 1, "one" ) has type ( Int, String ). Tuples are handy for returning several results from a function:

The Tuple module, which every module imports, works on pairs: Tuple.first, Tuple.second, Tuple.pair, Tuple.mapFirst, Tuple.mapSecond and Tuple.mapBoth. Tuples of comparable values, such as numbers and strings, compare component by component, so List.sort sorts them:

A tuple is encoded like a record, as a constructor with tag 0, but its fields stay in position order. For anything with more than three parts, or whose parts deserve names, use a record. A four-element tuple is rejected:

Section titled “Equality”

Limits

Section titled “Limits”
