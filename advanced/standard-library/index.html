Standard library

Elci’s standard library has two layers. The first is Elci’s core library: Elm’s core modules, with Elm’s names, argument orders and edge cases, bundled with the compiler, plus Value, Interval and Tx modules for the ledger’s multi-asset values, time ranges and transactions. Reach for it first. The second is Julc’s on-chain Java libraries, which you map in elci.toml. They fill the gaps, such as floor division, signature verification and matching whole addresses. This page shows what each layer offers, how to import it and which functions you will reach for most. Elm packages cannot be installed.

The core library

Section titled “The core library”

As in Elm, every module imports these for you:

ModuleImported asWhat it gives you
Basicsimport Basics exposing (..)min, max, abs, negate, clamp, compare, identity, always, not, xor, modBy, remainderBy, and the Order type
Listimport ListElm’s list functions: map, foldl, head, range, sum, member, sort, sortBy, filterMap and more
Maybeimport Maybe exposing (Maybe(..))withDefault, map, map2, map3, andThen
Resultimport Result exposing (Result(..))Ok, Err, map, map2, map3, andThen, withDefault, toMaybe, fromMaybe, mapError
Tupleimport Tuplepair, first, second, mapFirst, mapSecond, mapBoth
Stringimport StringfromInt, isEmpty, append, concat, join
Debugimport Debugtrace, which emits a Plutus trace

These need an import but no configuration:

ModuleImportWhat it gives you
Dictimport Dict exposing (Dict)Elm’s dictionaries: comparable keys, kept sorted
Mapimport Mapthe ledger’s association maps, for ledger data and keys that aren’t comparable
Arrayimport Arrayarrays with constant-time get and length
Valueimport Value exposing (Value)the ledger’s multi-asset values: lovelaceOf, quantityOf, add, geq and more
Intervalimport Intervaltime ranges such as the validity range: isEntirelyAfter, isEntirelyBefore, contains, without sentinel values
Tximport Txquestions about the transaction: signedBy, ownInput, outputsTo, continuingOutputs, mintedOf, inlineDatum and more
Bytesimport Bytesbyte-string builtins: slicing, integers, bits, hashes
Julc.Dataimport Julc.Data as Dataexplicit decode, encode and optional/Maybe adapters
Julc.Ledgerimport Julc.Ledger exposing (...)ledger types such as ScriptContext, PubKeyHash and TxOutRef

The types Int, Bool, String, Bytes, Data, List, Maybe (with Just and Nothing), Dict, Map and Array are built in.

Basics, List, Maybe, Result, Tuple, String, Dict, Map, Array, Value, Interval and Tx are written in Elci itself, and compiled with your code; a function you don’t call is never compiled into your script. Dict, Map and Array sit on top of Julc’s typed map and array libraries and of list operations the compiler specializes for their key and value types. Value sits on the protocol’s native value builtins (CIP-153). Interval and Tx read the ledger’s types directly. Every signature is on the core modules reference page, and lists, dictionaries, maps and arrays teaches them. Bytes get their own page: bytes, hashes and bits.

Julc’s Java libraries

Section titled “Julc’s Java libraries”

Julc ships its on-chain standard library as Java source, and the Elci compiler bundles it. To use a library, map a module name to its class, then import that module. Here is every bundled library, with the module names used on this site:

Map only what you import; an unused mapping is never loaded. The module names are yours to choose, except the core modules’ names: a [java-modules] key can’t be Interval, Tx or another core module. How mapping, types and rejections work in general is covered in Java libraries.

What “verified” means

Section titled “What “verified” means”

The compiler repository keeps an inventory of every public export. An export is compile-verified when an Elci wrapper with its concrete signature type-checks, links the real Java implementation and produces UPLC. That proves the signature maps correctly; it does not prove each function was evaluated with representative inputs through Elci. Julc tests the libraries’ behavior separately.

The current scan found 145 compile-verified exports, 41 unsupported signatures, 6 exports that return a Value, which Elci rejects, and 12 generic templates:

LibraryVerified exportsGaps
AddressLib4none
BitwiseLib9writeBits (uses PlutusData.ListData)
BlsLib0all 19 exports use BLS point types
ByteStringLib24none
ContextsLib23listIndex (uses PlutusData.ListData)
CryptoLib9none
IntervalLib9none
ListsLib17plus 6 generic programmatic exports
MapLib10concrete Data-based signatures only
MathLib8divMod, quotRem (return a Java Tuple2)
NativeValueLib0all 7 exports use JulcValue
OutputLib14none
ValuesLib1811 exports use unmapped Data subtypes or AssetEntry; 6 return a Value
TypedMapLib9 genericused by the core Map module
TypedArrayLib3 genericused by the core Array module

Using an unsupported export is a compile error (ELCI2105) that names the Java type involved. An export whose result can hold a Value is rejected the same way, because Java libraries don’t keep values in the ledger’s order; use the core Value module instead. ContextsLib and OutputLib are exempt: they only pass along the ledger’s own values. Some verified exports are public implementation helpers (their names often start with _ or end in Step). They are listed for completeness; do not build on them.

Section titled “An example”

Things to notice:

  • Java argument order. Library functions take the collection or subject first: Output.outputsAt outputs address. Core functions take it last, as in Elm: Tx.outputsTo credential ctx.
  • Optional results. A Java function that returns an Optional, such as ContextsLib.findOwnInput, gives a Julc optional. Convert it with Data.fromOptional before you match on Just and Nothing.
  • Core and Java together. Tx, Interval and Value are core modules; Address and Output are Java library calls. The payment carries the listing’s reference, so one payment can’t buy two listings (one payment per input).
  • Size. Library code is linked into your script: this validator is 1,297 bytes. Check the size after adding a library.

Most useful functions

Section titled “Most useful functions”

The tables give each export’s Elci type. Ledger.X means the type X from Julc.Ledger.

MathLib

Section titled “MathLib”
FunctionTypeNotes
signInt -> Int-1, 0 or 1
expModInt -> Int -> Int -> Intmodular exponentiation: Math.expMod 3 4 5 is 1
floorDiv, floorModInt -> Int -> Intround towards negative infinity: Math.floorDiv -7 2 is -4 and Math.floorMod -7 2 is 1
max, minInt -> Int -> Intthe prelude’s max and min do the same, for any comparable type
absInt -> Intthe prelude has abs
powInt -> Int -> Intlike the ^ operator (2 ^ 10 is 1024), except that a negative exponent gives 1, where ^ fails

Use the prelude’s max, min, abs and ^ rather than their MathLib versions: they need no mapping. Elci’s own // truncates towards zero, and modBy and remainderBy are in the prelude.

IntervalLib

Section titled “IntervalLib”
FunctionTypeNotes
containsLedger.Interval -> Int -> Boolbounds are inclusive
after, beforeInt -> Ledger.Intervalfrom a time onwards; up to a time
betweenInt -> Int -> Ledger.Intervalboth ends inclusive
always, neverLedger.Interval
isEmptyLedger.Interval -> Bool
finiteLowerBound, finiteUpperBoundLedger.Interval -> Intreturn -1 for an infinite bound

The -1 sentinel is easy to miss: finiteUpperBound (after 100) is -1, so “no end” looks like “ends at -1”. Use the core Interval module instead: its checks never hold on an infinite bound, and its start and end return Nothing for one. Map IntervalLib under another name than Interval, which is the core module’s.

The core Tx module covers these with typed results: Tx.signedBy, Tx.ownInput, Tx.continuingOutputs, Tx.outputsTo, Tx.valueSpent and Tx.datumOf. Prefer it. The txInfo... accessors (txInfoFee, txInfoInputs and so on) duplicate fields you can read directly, such as ctx.txInfo.fee. valuePaid and valueSpent return the ledger’s values, one per output or input.

OutputLib matches whole addresses, staking part included, where Tx.outputsTo and Tx.valuePaidTo match the payment credential only. Use it when the staking part matters. getInlineDatum fails the script for an output without an inline datum; Tx.inlineDatum returns a Maybe.

ValuesLib

Section titled “ValuesLib”

Use the core Value module for values: it reads, builds and compares them, and == works on its results. Julc’s ValuesLib builds values in its own order, so its exports that return a Value (add, subtract, negate, singleton and two helpers) are rejected with ELCI2105. The exports that only read a value still work, and a few have no direct equivalent in the Value module:

FunctionType
containsPolicyLedger.Value -> Bytes -> Bool
countTokensWithQtyLedger.Value -> Bytes -> Int -> Int
findTokenNameLedger.Value -> Bytes -> Int -> Bytes
uniqueTokenNameLedger.TxOutRef -> Bytes

Value.policies and Value.tokens answer the same questions with typed results.

ListsLib and MapLib

Section titled “ListsLib and MapLib”

Most ListsLib and MapLib exports work on List Data and Map Data Data, so you must encode every element with Julc.Data.encode first. Examples are ListsLib.containsInt : List Data -> Int -> Bool, ListsLib.hasDuplicateInts : List Data -> Bool and MapLib.lookup : Map Data Data -> Data -> JulcOptional Data. Prefer the typed core List, Dict and Map modules. ListsLib’s generic map, filter, any, all, find and foldl are covered in Java libraries.

What is missing

Section titled “What is missing”
  • BLS12-381 (BlsLib) and native values (NativeValueLib) have no usable exports yet.
  • Value at the boundary. A Value can’t be a datum, redeemer or parameter yet. Store a List ( PolicyId, TokenName, Int ) and rebuild it with Value.fromList.
  • Parts of Elm’s core are not available yet: Set (use a Dict k Bool), Char, most of String (length, toInt, split and so on), and the Float functions. Write small helpers yourself or use the Java libraries above.

Your own libraries

Section titled “Your own libraries”

You can write reusable libraries in Elci: ordinary modules under any source directory, listed in source-directories. There is no package registry yet; share them as source. See modules and imports. To reuse Java code, package it as a library JAR.
