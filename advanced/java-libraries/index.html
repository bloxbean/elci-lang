Java libraries

Elci can call on-chain libraries written in Java for Julc. They complement Elci’s core library: reach for them when the core has no equivalent, such as floor division, validity intervals or signature checks. This page shows how to map a Java library to an Elm-style module, how to package your own library as a JAR, how Java types appear in Elci, and which signatures are rejected and why.

How Java imports work

Section titled “How Java imports work”

A Julc on-chain library is a Java class annotated with @OnchainLibrary whose public static methods use a restricted, on-chain subset of Java. Elci never runs that Java on the JVM. Julc parses the library’s source code, compiles each method you use to typed PIR (Plutus IR) and hands it to Elci, which type-checks your calls and links the compiled code into your script.

Two consequences follow:

  • A library must be available as source. Compiled .class files alone are not enough.
  • A library call is compiled code, not a builtin. It costs whatever its Java implementation costs on-chain.

The rules:

  • You choose the module name. Julc.Math is a convention, not a built-in name. Nothing is mapped automatically, except Julc.TypedMap and Julc.TypedArray, which the core Map and Array modules use and which you may not remap.
  • Mappings load on import. An unused mapping is never read. Importing a module that is neither a source module nor mapped fails with ELCI2101: Missing source module: Julc.Nope; add Julc/Nope.elm under a source directory, or map a Java library to it under [java-modules].
  • Expose names explicitly. import Julc.Math exposing (floorDiv) works; exposing (..) is rejected for Java modules (ELCI2104). Qualified use through the alias always works. A name you expose explicitly takes precedence over a prelude name, so import Julc.Math exposing (max) replaces the prelude’s max in that module.
  • Core module names are taken. A [java-modules] key can’t be Basics, List, Maybe, Result, String, Tuple, Map, Array, Dict, Value, Interval, Tx, Set or Elci, or start with Elci..
  • Names are checked where you use them. A misspelled export is reported as ELCI2005: Unknown name 'Math.maximum'; check that the imported module exports it.

Use your own library JAR

Rules for library JARs:

  • Bundle every source the library needs, including records and other libraries it calls, even when they live in another JAR. Files are read in a deterministic order.
  • No duplicates. Two JARs providing the same class, or a JAR providing a class the compiler already bundles, is an error: Custom library conflicts with bundled source: org.julclang.stdlib.lib.MathLib.
  • A JAR must contain sources. Otherwise the build stops with No on-chain Java sources in .../libs/pricing.jar; bundle sources under META-INF/plutus-sources/.
  • A normal library JAR works if it also bundles its sources under META-INF/plutus-sources/.
  • The native executable supports JARs too, because it reads them as source files.

Java types in Elci

Section titled “Java types in Elci”

Julc describes each Java parameter and result type, and Elci maps it to an Elci type:

Java typeElci type
BigInteger, Integer, Long, int, long, short, byte, charInt
boolean, BooleanBool
StringString
byte[]Bytes
PlutusDataData
List<T>, JulcList<T>List t
Map<K, V>, JulcMap<K, V>Map k v
Optional<T>JulcOptional t (convert with Julc.Data.fromOptional)
JulcArray<T>Array t
void()
A record or sealed interface in library sourcea nominal type, such as Pricing.Quote
A ledger type such as PubKeyHash or TxOutthe matching Julc.Ledger type
An unbounded type parameter Ta type variable, specialized at each use

Imported types stay nominal. Pricing.Quote is not interchangeable with an Elci record of the same shape, and a PubKeyHash is not Bytes even though both are byte strings on-chain. Java’s Optional is not Elci’s Maybe either: their Data tags differ, so you convert explicitly with Julc.Data.fromOptional and Julc.Data.toOptional (see core modules).

Records and sealed interfaces declared in the library class, or at the top level of its package, can be named through the module alias (Pricing.Quote) or exposed (exposing (Quote)). Two exposed types with the same name are rejected as ambiguous; map the other package to a second module name.

Imported records and sum types

Section titled “Imported records and sum types”

Julc approves a set of operations for each imported type it has verified, and Elci enables exactly those:

OperationWhat you can write
ConstructPricing.Quote 250 True, Buy 3. Record fields are in Java declaration order.
MatchExhaustive case over a sealed interface’s records, such as Buy value and Cancel.
ProjectField access: quote.amount.
Equality== and /=, with Java equals semantics.
Encode and decodeJulc.Data.encode and Julc.Data.decode.
BoundaryUse as a validator’s datum, redeemer or parameter type.

To expose a sum’s constructors unqualified, write exposing (Action(..)). Types with special layouts get fewer operations. The ledger’s Value is the core Value type, with its own module and ==. Apart from Julc’s context accessors, no Java library may return one (below). Types that contain it, such as TxOut, keep field access and matching but have no equality, decoding or boundary use.

Generic methods

Section titled “Generic methods”

A generic Java method such as firstOr is a template. Elci imports it as a generic function and asks Julc to compile a separate copy for each concrete type you use it at. In the example above, Pricing.firstOr [ 10, 20 ] 0 compiles a copy for Int, and firstOrder compiles another for the Elci record Order. Elci’s own records, tuples and unions are valid type arguments.

Every type parameter must have a Plutus Data encoding: an integer, bytes, string, Bool, Data, a record or union (Elci or imported), or a list, map or JulcOptional of these. A function or () is rejected before anything is compiled:

A type that contains a Dict is rejected too. A Dict must keep its keys in ascending order, and a library could build one that doesn’t, so pass it a Map or a List and build the dictionary with Dict.fromList:

A type that holds a Value is rejected for the same reason: every value must stay in the ledger’s canonical order, and a library could build one that isn’t.

Calls are strict and curried, in Java argument order: each argument is evaluated once, even under partial application.

Equality inside a template

A template that compares values of its type parameter uses Data equality, whatever the type. For a type without equality, such as a Map or a type containing one, that comparison is sensitive to map order. Avoid instantiating such templates at those types.

What is rejected, and why

Section titled “What is rejected, and why”

Elci never pretends an unsupported Java type is plain Data. A signature it cannot represent faithfully is rejected when you use it, with the reason:

Java signatureResult
A type Julc cannot map, such as Tuple2, PlutusData.ListData, JulcValue or BLS pointsELCI2105: org.julclang.stdlib.lib.MathLib.divMod: Unsupported on-chain source type: Tuple2<BigInteger, BigInteger>
A result that can hold a ledger Value, directly or in a record or union field, except in ContextsLib and OutputLibELCI2105: org.julclang.stdlib.lib.ValuesLib.add: returns a Value, which Java libraries do not keep in the ledger's canonical order; use the core Value module
A bounded type parameter, such as <T extends Comparable<T>>ELCI2105: acme.Pricing.largest: Type parameter T extends Comparable<T> has a bound; generic library methods support only unbounded type parameters
A raw container, such as List without a type argumentELCI2105: acme.Pricing.count: Raw or invalid container signature: List
Overloads with different signaturesELCI2105: acme.Pricing.scale: Ambiguous overloaded library export acme.Pricing.scale: overloads with different signatures cannot be told apart on-chain; give them distinct names
A function, () or a type containing a Dict or a Value as a generic type argumentELCI3003 (above)
exposing (..) on a Java moduleELCI2104: Java modules cannot be imported with exposing (..); list the exported names you use

Some library shapes stop the whole library from loading, so no export of it can be used:

  • A wildcard type such as JulcList<?> fails with Cannot resolve type: ?.
  • A parameterized record such as record Box<T>(T value) fails with Unknown type: T.

While a class has an ambiguous overload, Elci reports that overload for every export of the class. Give overloads distinct names. Overloads with identical Elci signatures, such as ByteStringLib’s two integerToByteString methods, are exported once.

Linking and cost

Section titled “Linking and cost”

In a validator, each library function and each generic specialization is linked once per script and shared by all handlers. Zero-argument library values are evaluated once when the script starts, like top-level values. In function programs (elci eval and each test), a closed copy is inlined at each use. A library import therefore adds its compiled size to your script; see costs and performance for how to measure it.
