Your first validator

In this tutorial you create a small validator, read every file that elci init generates, and check, test and build it. Then you change it to require a second signature and update its tests. You need elci on your PATH (see Installation).

What a validator does

Section titled “What a validator does”

On Cardano, funds can be locked at a script address. Whenever a transaction tries to spend them, the ledger runs the script, called a validator, and the spend only happens if the validator approves. A spending validator receives four things:

  • Parameters that you fix when you deploy the script, such as the owner’s key.
  • The datum: data stored with the locked output when it was created.
  • The redeemer: data that the spending transaction supplies.
  • The script context: the whole transaction being validated, including who signed it.

It returns True to approve the transaction. Returning False, or failing during evaluation, rejects it. Validators can also control minting, reward withdrawals and governance actions; this tutorial sticks to spending.

Create the project

Section titled “Create the project”

elci init creates this layout:

  • Directorymy-contract/
    • elci.toml project configuration
    • README.md
    • .gitignore ignores build/
    • Directorysrc/
      • Main.elm the validator
    • Directorytests/
      • MainTest.elm two transaction scenarios

The configuration

Section titled “The configuration”
  • [project] says where your modules live, which on-chain target to compile for (Plutus V3), and which Julc version the compiler must match.
  • [validators.main] declares one script called main. Its spend handler is the function spend in module Main, and it takes one deployment parameter called owner.
  • boundary = "julc-strict-v1" selects strict decoding of the data the script receives. It is currently the only boundary policy.

The source code doesn’t say how it is deployed. The configuration does, so the same function could be reused in another validator.

The validator

Section titled “The validator”

Line by line:

  • module Main exposing (spend) names the module (it must match the file path src/Main.elm) and makes spend visible to the configuration and to tests.

  • import Julc.Ledger exposing (PubKeyHash, ScriptContext) brings in two Cardano ledger types.

  • The signature lists the arguments in the order the handler receives them:

    ArgumentTypeMeaning
    ownerPubKeyHashThe owner parameter: the hash of the owner’s public key
    _()The datum. () (unit) means “no information”
    _()The redeemer, also unit
    ctxScriptContextThe transaction being validated

  • The body reads ctx.txInfo.signatories, the key hashes that signed the transaction, and uses List.any to check whether one of them is the owner. \signer -> signer == owner is an anonymous function (a lambda). The core Tx module has the same check as Tx.signedBy owner ctx, after import Tx.

The _ pattern ignores an argument. The datum and redeemer are still decoded strictly before spend runs, so they must be unit data.

The tests

Section titled “The tests”

A Scenario describes one transaction against a validator of your project:

  • Scenario.key "owner" derives a deterministic test key hash from a name.
  • Scenario.spend "main" (Scenario.outRef "main" 0) Scenario.unit spends an output locked at validator main’s address, with a unit datum.
  • Scenario.parameters [ Data.encode owner ] supplies the deployment parameters, in the order declared in elci.toml. Data.encode turns an Elci value into on-chain data.
  • Scenario.signedBy adds a signer, and Scenario.expectFailure says the validator must reject the transaction.

Only the exposed declarations of type Scenario are tests. owner and transaction are helpers.

Run the tests

Section titled “Run the tests”

Each scenario compiles the validator exactly as elci build does, applies the parameters, builds a complete ledger context for the transaction and runs the script. cpu and mem are the execution budget the script used. The ledger charges fees for these units and limits how many a transaction may use.

Build it

Section titled “Build it”

The build writes one directory per validator:

  • Directorybuild/
    • Directoryvalidators/
      • elci-outputs.json the files Elci owns
      • Directorymain/
        • abi.json how your types are encoded
        • validator.flat the script in FLAT encoding
        • validator.plutus a Plutus V3 text envelope
        • validator.plutus.json the Julc artifact for Cardano Client Lib

Apply the parameters

Section titled “Apply the parameters”

Before you deploy, you apply the real parameter values. elci apply takes each value as Plutus Data in cardano-cli’s JSON format. A PubKeyHash is 28 bytes, written as hex. These two keys are placeholders:

apply first checks each value against the parameter’s type. The applied script has its own hash, which determines its address on-chain. Parameterized validators explains the format.

What you learned

Section titled “What you learned”
  • elci.toml decides how functions are deployed: [validators.<name>], handler keys and parameters.
  • A spend handler receives parameters, datum, redeemer and context, and returns Bool.
  • elci check catches mistakes, including a handler that doesn’t match its configuration.
  • elci test runs transaction scenarios against the exact script that elci build writes.
