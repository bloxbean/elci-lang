Elci AI starter pack

Read this entire page before generating any Elci code. It states the Elci subset of Elm, the project format, the on-chain rules and the mistakes agents make most often. Every rule, signature and message here was checked with the Elci CLI (elci 0.1.0-dev / julc 0.1.0-pre20-ebaf028-SNAPSHOT).

This page is optimized for AI ingestion, not for humans. For the tutorial, see your first validator. Sections are numbered so you can cite them.

1. What Elci is, and what it is not

Section titled “1. What Elci is, and what it is not”
  • Elci compiles .elm source written in an Elm 0.19 syntax subset into Plutus V3 scripts for Cardano. It lowers to typed PIR and uses Julc’s backend (validator wrapper, UPLC optimizer, evaluator). The only target is plutus-v3-pv11-uplc-1.1.0.
  • On-chain only. Elci code is validator logic. Building transactions is done off-chain with other tools (for example Cardano Client Lib, reading validator.plutus.json).
  • Not browser Elm. There is no Html, Browser, Cmd, Sub, port, JSON decoders or runtime.
  • No Elm packages. elm.json is not used. There is no package manager.
  • Elm’s core library, partly. Basics, List, Maybe, Result, Tuple, String and Debug are imported by default, as in Elm, with Elm’s names and argument orders, but String has only five functions and Debug only trace. Dict exists with Elm’s API (import Dict exposing (Dict)); Set, Char and Float do not exist (section 3.3). A Value module (import Value exposing (Value)) handles the ledger’s multi-asset values (section 7). Tx and Interval answer questions about the transaction and its validity range (section 8); prefer them to hand-written list walks and to Julc’s ContextsLib and IntervalLib.
  • Strict, not lazy. Every let value and every function argument is evaluated (section 4).
  • Configuration decides deployment. Handlers are ordinary functions; elci.toml says which function serves which ledger purpose (section 2).
  • Development preview. Not production-ready. No CIP-57 blueprints, no language server.

2.1 Rules

Section titled “2.1 Rules”
  1. [project] requires source-directories, target = "plutus-v3-pv11-uplc-1.1.0" and julc-version = "0.1.0-pre20-ebaf028-SNAPSHOT" (must equal the compiler’s pinned version; elci --version prints it). Optional: library-jars; expected-abi only in function projects.
  2. A project has either one or more [validators.<name>] tables or one [entrypoint], never both.
  3. [validators.<name>]: name is 1–64 chars of a-z, 0-9, -, _, starting with a letter. boundary = "julc-strict-v1" is required. At least one handler key: spend, mint, withdraw, certify, vote, propose, each "Module.function" naming an exposed function. One table = one script = one hash.
  4. parameters = ["a", "b"]: deployment parameters in application order; names match [a-z][A-Za-z0-9_]*. Every handler of the table receives all of them as leading arguments, with the same types.
  5. spend-datum = "required" (default), "optional" or "absent"; requires a spend handler.
  6. expected-abi = "path": check, build and apply fail if the ABI (abi.json) differs.
  7. [java-modules]: "Module.Name" = "fully.qualified.Class". You choose the module name. Julc.TypedMap and Julc.TypedArray are reserved, and so are the core module names (Basics, List, Maybe, Result, String, Tuple, Map, Dict, Array, Set, Value, Interval, Tx, Elci) and names starting with Elci..
  8. [tests]: source-directories, default ["tests"].
  9. TOML subset: one key = value per line; values are quoted strings without escapes or single-line arrays of quoted strings; comments are whole lines starting with # (no trailing comments); unknown tables and keys are errors.

3. The language subset

Section titled “3. The language subset”

3.1 Allowed

Section titled “3.1 Allowed”
  • Modules: module A.B exposing (f, T, U(..)) or exposing (..); import M as N exposing (x, T(..)). Imports must be acyclic. Every module has Elm’s default imports (section 8). Own declarations shadow imports; a name two imports expose is ambiguous where used, except that a name listed in exposing beats a default import.
  • Every top-level declaration needs a type signature. Local (let) definitions may have one.
  • Functions, lambdas \a b -> ..., currying, partial application, |>, <|, >>, <<. Operators as functions: (+), (::), (<), as in List.foldl (+) 0 xs. ^ is integer power.
  • Rank-1 generics (a -> a), specialized per concrete use. Local helpers may be used at several types. Elm’s constrained variables: a signature variable compared with </compare must be named comparable…, one appended with ++ appendable…, both compappend….
  • Types nothing determines need no annotation ([] == [], List.length [], Data.encode Nothing), except where a value is created: Data.decode and generic Java functions (ELCI3001).
  • Self-recursion and mutually recursive functions (top-level or local).
  • Types: Int (arbitrary precision), Bool, String, (), Bytes, Data, List a, Maybe a, Result error value, Order, Dict k v (comparable keys), Map k v, Array a, Value, tuples of 2 or 3, closed records, custom types (generic, recursive).
  • type alias R = { x : Int } (also a constructor R 1); type T a = A a | B.
  • Records: { x = 1 }, r.x, { r | x = 2 }, destructuring { x, y } in parameters and let. Accessor functions as in Elm: .x is \r -> r.x, so List.map .amount payouts works. A field of a qualified value: Config.settings.fee. Write qualified names without spaces.
  • case with nested patterns: constructors, [], [ a, b ], a :: rest, tuples, record fields, as, _, (), True/False, Int and String literals. Exhaustive and no unreachable branches.
  • if c then a else b (else required), let ... in, ++ on String and List, ::.
  • <, <=, >, >=, compare, min, max, List.sort on comparable types: Int, String (UTF-8 byte order), Bytes, ledger hashes (PubKeyHash, ScriptHash, PolicyId, TokenName, TxId, …), and lists and tuples of these.
  • Comments --, {- nested {- ok -} -}, doc comments {-| -}.

4. Evaluation rules

Section titled “4. Evaluation rules”
  1. Strict. Every let binding is evaluated before the body, even if unused. An unused let bad = 10 // 0 fails the script.
  2. Selective forms only: if, case, &&, || evaluate just the taken branch/operand. Put cheap, likely-false checks first inline; a check bound in let is always paid for.
  3. Order: function, then arguments left to right; let bindings in dependency order, ties in source order; record fields, list and tuple elements in source order; record update: base, then new fields. Arguments are always evaluated: Maybe.withDefault expensive m computes expensive even for a Just, and (&&) a b as a function evaluates b. Use case or the && operator to skip work.
  4. Top-level values (zero-argument declarations) reachable from any handler run once per script execution before purpose dispatch, so every purpose pays for them. Make expensive ones functions (limit : () -> Int).
  5. Negation follows Elm 0.19: f -1 passes -1; scale -x 10 passes -x; x - 1 and x-1 subtract; x -1 is an application of x.
  6. Integers: // truncates towards zero (-7 // 2 is -3). modBy d v has the divisor’s sign (modBy 3 -7 is 2); remainderBy d v has the value’s sign (remainderBy 3 -7 is -1). Division by zero fails the script.
  7. Failure: a runtime failure (division by zero, out-of-range byte, failed decode) or a handler result of False rejects the transaction. There are no exceptions to catch.
  8. Equality (==, /=): Int, Bool, String, (), Bytes, ledger hashes of the same type, Value (exact), Data (exact structure), lists, tuples, records, Maybe, Dict (same bindings) and custom types of these; imported types with approved equality. Not Map, functions, Array, TxOut, TxInInfo, TxInfo. Both operands are evaluated once, left to right.
  9. Ordering (<, <=, >, >=, compare, min, max, List.sort): Int numerically; String by UTF-8 bytes ("Zebra" < "apple"); Bytes and ledger hashes lexicographically by unsigned byte, a proper prefix first (#ff > #0001); lists lexicographically; tuples by component. Every order agrees with ==.
  10. Integer power: 2 ^ 10 is 1024; ^ binds tighter than * and groups right; a negative exponent fails the script.

5. Data encoding and Julc.Data

Section titled “5. Data encoding and Julc.Data”

Datums, redeemers and parameters cross the script boundary as Plutus Data and are decoded strictly (tags, arity, field kinds checked; malformed data fails the script, never Nothing).

Julc.Data (import Julc.Data as Data): decode : Data -> a, encode : a -> Data, fromOptional : JulcOptional a -> Maybe a, toOptional : Maybe a -> JulcOptional a. The decoded type must be known where decode is used; annotate otherwise (ELCI3001: Cannot determine the type converted by Julc.Data.decode; add a type annotation). == on Data compares structure exactly, so a datum check needs no decoding: Tx.inlineDatum out == Just (Data.encode expected). Elci’s encodings are deterministic, except that a Map’s encoding follows its insertion order: Data.encode of two maps with the same bindings may differ, so compare their sorted toList or use a Dict. Tests build datums and redeemers with Data.encode.

6. Handler signatures

Section titled “6. Handler signatures”

parameters come first, in the order listed in elci.toml. The last argument is always ScriptContext (import Julc.Ledger exposing (ScriptContext)). The result is Bool. Handlers must be exposed and have concrete types.

Handler keyRequired type
spendparams -> datum -> redeemer -> ScriptContext -> Bool
spend + spend-datum = "optional"params -> Maybe datum -> redeemer -> ScriptContext -> Bool
spend + spend-datum = "absent"params -> redeemer -> ScriptContext -> Bool
mint, withdraw, certify, vote, proposeparams -> redeemer -> ScriptContext -> Bool
  • Datum, redeemer and parameter types need a strict Data boundary: your records and custom types, Int, Bool, String, Bytes, (), tuples, lists, Dict, Map, Maybe, and ledger types such as PubKeyHash, TxOutRef, Credential, PolicyId, TokenName. Not: functions, Array, ScriptContext, TxOut, TxInfo, Value (for an amount of tokens, store List ( PolicyId, TokenName, Int ) and call Value.fromList).
  • Use () for an unused redeemer or datum. Only the selected handler’s datum and redeemer are decoded.
  • A validator always checks the purpose; purposes without a handler are rejected.
  • Parameters are decoded but not validated on-chain; elci apply validates them off-chain. Exception: the key order of a Dict (in a datum, redeemer or parameter) is checked on every run.

Rules:

  • PubKeyHash, ScriptHash, PolicyId, TokenName, TxId, DatumHash are distinct from Bytes; compare like with like, or use .hash. key == Bytes.fromString "k" with key : PubKeyHash is ELCI2002: The two sides of == have different types: the left is `PubKeyHash`, but the right is `Bytes`, with a hint to wrap the bytes with the constructor. token.name is ELCI2010: Unknown field 'name' of TokenName; write token.hash.
  • Signature check: Tx.signedBy key ctx.
  • Ledger hashes order like bytes: List.sort sorts a List PubKeyHash. TxOutRef and other ledger records are not comparable.
  • Construct ledger values qualified: import Julc.Ledger as Ledger then Ledger.PubKeyHash bytes, Ledger.TxOutRef (Ledger.TxId bytes) 0.
  • Value (out.value, tx.mint) is the core Value type: read it with the Value module (section 8), Value.lovelaceOf value, Value.quantityOf policy tokenName value. Build asset ids with import Julc.Ledger exposing (PolicyId(..), TokenName(..)): PolicyId bytes, TokenName (Bytes.fromString "BADGE"). Ada is PolicyId Bytes.empty with TokenName Bytes.empty; use Value.lovelace and Value.lovelaceOf.
  • Every Value is canonical (policies and token names ascending, no zero quantity), so == on values is exact. TxOut, TxInInfo and TxInfo, which contain a Value, have no equality. A Value cannot cross the boundary yet. In tx.mint, burns are negative quantities.
  • JulcOptional has no equality; convert with Data.fromOptional.

“After the deadline”: Interval.isEntirelyAfter deadline tx.validRange (strict; a range without a finite start fails, and so does an empty range’s PosInf start, as in Aiken’s stdlib v2). “Before the deadline”: Interval.isEntirelyBefore deadline tx.validRange. Bytes (import Bytes; builtins; the byte string is the last argument; compare with ==, <, compare):

Debug (imported by default): trace : String -> a -> a. Both arguments are evaluated first, so the message is not emitted if the value fails. Traces cost budget and bytes.

Expect (tests only; import Expect exposing (Expectation)):

Scenario (tests only; import Scenario exposing (Scenario); the String is the validator name from elci.toml):

Test discovery: a test is an exposed, zero-argument, top-level declaration of type Bool, Expectation, Scenario or Property. Unexposed declarations are helpers. Test modules live in tests/, may import src modules and [java-modules], and must not share a name with a source module. Only test modules may import Expect, Scenario and Property.

9. Java libraries (Julc stdlib)

Section titled “9. Java libraries (Julc stdlib)”

Java libraries fill gaps in the core library; prefer a core function when one exists (max, abs, ^, List.member). Map a class, then import the module. Nothing is mapped by default. Use explicit exposing lists (exposing (..) is rejected for Java modules). Java argument order: the collection or subject comes first.

FunctionType
Math.floorDiv, floorModInt -> Int -> Int (round towards negative infinity; // truncates)
Math.expModInt -> Int -> Int -> Int
Math.signInt -> Int

Crypto.verifyEd25519Signature (CryptoLib)Bytes -> Bytes -> Bytes -> Bool (key, message, signature)

Use the core Tx and Interval modules instead of ContextsLib and IntervalLib. IntervalLib’s finiteLowerBound and finiteUpperBound return -1 for an infinite bound, a sentinel that makes “no end” look like “ends at -1”. Interval and Tx are core module names: a [java-modules] key can’t be either, and a Java module should not be aliased as either.

Unsupported signatures (for example MathLib.divMod, all of BlsLib) are ELCI2105, and so is every export whose result can hold a Value (ValuesLib.add, ValuesLib.singleton), except in ContextsLib and OutputLib, which pass along the ledger’s own values: use the core Value module (section 8), not ValuesLib. Generic Java methods are specialized per use; type arguments must be Data-encodable and must not contain a Dict or a Value (ELCI3003).

10. The CLI loop

Section titled “10. The CLI loop”

Run from the project directory (or pass it as the first argument). Exit status is 0 on success and 1 on any error, failing test, failed evaluation or when no tests are found.

  1. elci check: compile every validator (or the entrypoint); prints one line each: validator badge (mint): checked; 299 FLAT bytes; plutus-v3-pv11-uplc-1.1.0. Fix every error first.
  2. elci test: run tests; prints PASS/FAIL Module.test (cpu N, mem M) then N passed, M failed (seed S). Options: --match <substring> (case-insensitive on Module.test), --seed <n> (reproduce), --fuzz <runs> (property runs, default 100).
  3. elci eval (function projects only): prints the value in Elci syntax, then cpu N, mem M, then trace: lines; --builtins lists the last 20 builtin calls; failure prints evaluation failed: <reason>.
  4. elci build: writes build/validators/<name>/{validator.flat, validator.plutus, validator.plutus.json, abi.json}; --validator <name> selects.
  5. elci apply --validator <name> --param name=<json>: applies parameters, checking them off-chain. JSON is cardano-cli detailed schema: {"int": 5}, {"bytes": "hex"}, {"list": [...]}, {"map": [{"k": ..., "v": ...}]}, {"constructor": 0, "fields": [...]}; @file reads a file. A Dict parameter must list its keys strictly ascending (integers numerically, bytes lexicographically).

Error format: the first line is path:line:col: ELCIxxxx: message. Then come a blank line, the source line as N| code, a caret line under the reported token or expression, and zero or more Hint: ... lines. For a validator, a blank line and In .../elci.toml:<line>: [validators.<name>] follow. The report ends with the command that explains the code:

Parse the first line, whose form never changes, and apply the hints: they name a close name, a conversion (String.fromInt, Bytes.fromString, .hash, Maybe.withDefault, Value.lovelaceOf) or an import to add. A run reports every error it finds, in source order and separated by blank lines, up to 20, then ... and N more and a count such as 3 errors. Each top-level declaration reports its first error. Type errors appear only once there are no syntax, import or qualified-name errors, so rerun after each round of fixes. A long type mismatch adds It is: and It needs: lines with the first difference marked. elci explain ELCI2002 explains a code with an example and its fix. Configuration and command-line errors start with elci: ELCI4001:. For tools, --report=json on check, build, eval and test prints each error on stderr as one JSON object on its own line (JSON Lines), with code, path, line, column, message, hints (an array), excerpt and context (the validator’s elci.toml line, or null); prefer it to parsing text. Results and test output stay text.

12. Anti-patterns agents get wrong

Section titled “12. Anti-patterns agents get wrong”
  1. Using Elm APIs Elci lacks (Set, Debug.log, String.length, String.toInt, List.map4). Use section 3.3. The core functions in section 8 do exist; use them rather than writing your own or mapping Julc.Math.
  2. Forgetting imports. Dict, Map, Array, Value, Interval, Tx, Bytes, Julc.Data must be imported; Basics, List, Maybe, Result, String, Tuple and Debug are implicit. Julc.* Java modules also need a [java-modules] mapping.
  3. Omitting type signatures on top-level declarations (ELCI2004).
  4. Wrong handler shape. Parameters first, then datum (spend only), redeemer, ScriptContext, returning Bool. Use () for unused datum/redeemer. Expose the handler.
  5. Mixing Bytes and PubKeyHash. Keep keys as PubKeyHash; use .hash only when bytes are needed.
  6. Expensive checks in let or before cheap ones: they always run. Write cheap && expensive inline.
  7. Expensive top-level values in multi-purpose scripts: every purpose pays. Use functions.
  8. Assuming record field order in Data: records encode fields sorted by name.
  9. Assuming Maybe = Java Optional tags: convert with Data.fromOptional / Data.toOptional.
  10. Julc’s IntervalLib for deadlines, whose finiteLowerBound/finiteUpperBound return -1 for an infinite bound. Use Interval.isEntirelyAfter/isEntirelyBefore, and mind that they are strict.
  11. Storing Array in data, or building big maps with Map.fromList (quadratic; a 100-entry map exceeds a transaction’s memory budget). Keep lists in data, convert with Array.fromList once; build keyed data with Dict.fromList (O(n log n)).
  12. Data.decode without a known type (ELCI3001). Annotate the binding.
  13. Missing Scenario.parameters: a scenario must pass every validator parameter, in order.
  14. Importing Expect/Scenario/Property from src (ELCI2101). They are for tests/ only.
  15. x -1 meaning subtraction. It is an application; write x - 1.
  16. Float, /, %: integers only; //, modBy, remainderBy, ^ (non-negative exponents).
  17. exposing (..) on Java modules or relying on Java overloads (rejected).
  18. Trusting parameters on-chain: they are not validated; validate with elci apply before deployment.
  19. Very large integer literals with elm-format: elm-format 0.8.8 corrupts literals beyond 64 bits.
  20. Plain type variables with < or ++. Name them comparable or appendable (ELCI2003).
  21. Sorting records with List.sort. Records and custom types are not comparable: use List.sortBy (\r -> r.key) or List.sortWith.
  22. Reading a PlutusTx Either as Result. Ok is constructor 0 and Err 1, the reverse of Left/Right.
  23. Expensive Maybe.withDefault defaults. The default is always evaluated; use case instead.
  24. Map for your own keyed data. Use Dict when keys are comparable: it is sorted, has == and builds in O(n log n). Keep Map for ledger maps (txInfo.withdrawals, txInfo.redeemers) and keys that are not comparable.
  25. Unsorted Dict data. A Dict in a datum, redeemer or parameter must have strictly ascending keys, or it fails to decode. Build test data with Data.encode (Dict.fromList ...); off-chain, sort keys in Elci’s order, not CBOR’s canonical order (which puts shorter byte strings first).
  26. Reading values through ValuesLib. Use the core Value module; Java exports that return a Value are rejected (ELCI2105). == on values is exact, so use Value.geq for “pays at least”. Value.lovelaceOf tx.mint is 0, and a burn is a negative quantity in tx.mint. import Julc.Ledger exposing (Value(..)) is ELCI2104: values come from the Value module.
  27. Hand-written context walks. List.any (\s -> s == key) tx.signatories, a case on scriptInfo to find the own input or policy, or a filter over tx.outputs by credential: use Tx.signedBy, Tx.ownInput, Tx.ownPolicy and Tx.outputsTo.
  28. Untagged payment checks. Value.lovelaceOf (Tx.valuePaidTo (PubKeyCredential seller) ctx) >= price lets one output pay for two script inputs (double satisfaction). See section 13.
  29. token.name on a TokenName. Its bytes are token.hash; there is no .name field.

13. Security checklist for validators

Section titled “13. Security checklist for validators”

The escrow, marketplace and order-swap example projects apply the items that concern spend validators and test each attack (examples/escrow, examples/marketplace, examples/order-swap; their sources are in /ai/examples.json).

  1. Tag every payment against double satisfaction. When two inputs of one script can each require a payment to the same party, one output satisfies both checks. Require the paying output to carry the spent output’s reference as its inline datum:

    Never accept an untagged Tx.valuePaidTo total. Write a scenario that pays with another input’s tag (Scenario.withDatum (Data.encode (Scenario.outRef "listing" 1))) and expects failure.

  2. One script input per transaction when outputs are matched by address. An output returned to the script carries the script’s datum, not a tag, so one returned output could stand for two inputs. Count the inputs whose resolved.address.credential is the own input’s and require exactly one.

  3. Check the whole value that stays. For an output back to the script, compare its whole value with Value.geq output.value expected, where expected is everything that must stay (for example Value.subtract own.resolved.value taken), not just one token: otherwise the spender keeps the lovelace and the other tokens. To stop padding with junk tokens as well, require Value.withoutLovelace output.value == Value.withoutLovelace expected and Value.lovelaceOf output.value >= Value.lovelaceOf expected.

  4. Use Value.geq or >= for “pays at least”, never ==, which rejects a payment with extra lovelace or tokens. Use == when exactness is the rule, as for Tx.mintedOf policy ctx in a minting policy.

  5. Check signatures with Tx.signedBy for every privileged action (cancel, refund, update, withdraw), and write a scenario where a stranger signs.

  6. Bound numbers taken from datums and parameters. Parameters are not validated on-chain: check a fee in basis points is between 0 and 10000, and amounts are positive (amount > 0), before using them.

  7. Deadlines use Interval. isEntirelyAfter/isEntirelyBefore fail for a transaction without a validity range. They are strict; test the boundary with a property over offsets around the deadline.

  8. Payees are matched by payment credential. Tx.outputsTo ignores the staking part: whoever builds the transaction chooses the payee’s staking part. To protect a payee’s staking rights, store their full Address and compare output.address.

  9. Minting policies check the whole mint under their policy: Dict.toList (Tx.mintedOf policy ctx) == [ ( TokenName name, quantity ) ] rejects extra token names.

15. Checklist before generating Elci code

Section titled “15. Checklist before generating Elci code”
  1. Is every top-level declaration annotated, and every module name equal to its file path?
  2. Did I avoid every Elm API in section 3.3 and import Dict/Map/Array/Value/Interval/Tx/Bytes/Julc.Data where used?
  3. Does each handler match section 6, with parameters first, and is it exposed and listed in elci.toml?
  4. Are datum, redeemer and parameter types Data-encodable (no functions, Array, Value, TxOut)?
  5. Do I compare PubKeyHash with PubKeyHash (or .hash with Bytes), never mixed?
  6. Are cheap checks first and inline, and expensive work kept out of let and top-level values?
  7. Is every Julc.* module I import mapped under [java-modules], with explicit exposing only?
  8. Do my scenarios pass all parameters, and do they cover success, each failure path and a property?
  9. Did I use Tx and Interval rather than hand-written context walks, ContextsLib or IntervalLib?
  10. Does the validator pass the security checklist (section 13), with a scenario for each attack?
  11. Did I run elci check, then elci test, and fix every error before elci build?
