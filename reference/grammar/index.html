Grammar

This page is Elci’s formal grammar: the lexical grammar, the layout rules and the syntactic grammar. It describes what the compiler’s parser accepts, including the edge cases. For a summary of the syntax, see the language reference; for what programs mean, the rest of that page.

The grammar covers syntax only. A program that matches it can still be rejected later, for example for a type error, a missing signature or an unknown name.

The same grammar is kept in the repository as docs/GRAMMAR.md. A test parses every complete module it shows, and the syntax corpus has a module for each area of the grammar. The repository also has a tree-sitter grammar that follows it, for highlighting and folding in Neovim, Helix and Zed.

Notation

Section titled “Notation”

The grammar uses the W3C EBNF notation of the XML 1.0 specification (section 6):

NotationMeaning
A ::= ...defines the symbol A
"text"the literal text
[abc], [^abc]one character from the set, or one not in it
#xNthe character with hexadecimal code point N
A BA followed by B
A | BA or B
A?, A*, A+A optionally, zero or more times, one or more times
A - Bwhat A matches, except what B matches
( ... )grouping
/* ... */a comment

Elci’s layout needs two additions, used only in the syntactic grammar:

NotationMeaning
X<f>the symbol X read with the floor f, a column (see Layout); X<none> has no floor
CONT<f>matches nothing; allowed only when the next token is not a boundary for the floor f
COL<c>matches nothing; allowed only when the next token is in column c

The lexical grammar is over characters. The syntactic grammar is over tokens: a quoted string there means a token with that text, and the lexer has already removed whitespace and comments.

Lexical grammar

Section titled “Lexical grammar”

The lexer reads the source from left to right and produces tokens. Between tokens it skips whitespace and comments. At each position it tries the rules in this order: whitespace, line comment, block comment, name, integer, string, symbol.

Whitespace and positions

Section titled “Whitespace and positions”
  • A tab outside a string or comment is an error: ELCI1001: Tabs are not permitted; use spaces for Elm layout. Tabs inside strings and comments are allowed.
  • Every token has a line and a column, both counted from 1. The column counts characters (Java chars) from the start of the line. A newline is #xA; #xD is whitespace, so CRLF line endings work.

Comments

Section titled “Comments”
  • Block comments nest: {- a {- b -} c -} is one comment.
  • The lexer scans a block comment from left to right: each {- opens a nested comment, and each -} closes one. So {- a{-} is unterminated, since its {-} opens a comment (ELCI1001: Unterminated block comment).
  • {-| ... -}, Elm’s doc comment, is an ordinary block comment. The compiler does not read it.
  • An unterminated block comment is ELCI1001: Unterminated block comment.
  • Comments are not tokens. They take no part in layout: a token after a comment is placed by its own line and column.

Names and reserved words

Section titled “Names and reserved words”
  • _ alone is the wildcard pattern.
  • if, case and let are keywords where an expression starts. alias is a keyword only after type. True and False are the Boolean literals.

Integers

Section titled “Integers”
  • An integer is decimal and has no size limit.
  • A . followed by a digit right after an integer is an error: ELCI1001: Float is unsupported; represent fractional amounts using an explicit integer scale.
  • 0xFF and 1e3 are not literals: they read as the integer 0 or 1 followed by a name.

Strings

Section titled “Strings”
  • A string is on one line. A raw line break in it is ELCI1001: Use an escaped newline in a string.
  • Any other escape, such as \u{0041}, is ELCI1001: Unsupported string escape.
  • There are no character literals and no triple-quoted strings.

Symbols

Section titled “Symbols”
  • The two-character symbols are tried first, so a+++b reads as a ++ + b.
  • Any other character is ELCI1001: Unsupported character 'c', for example %, ', ` and !.
  • / is a symbol but not an operator: the parser rejects it (see Operators).

Layout

Section titled “Layout”

Indentation is significant. The parser reads it from token columns; it does not insert layout tokens. These are the exact rules.

New line. A token starts a new line when its line is after the line of the token before it.

Floors and boundaries. Every expression and type is read with a floor f, a column. A token is a boundary for the floor f when it is the end of the input, or when it starts a new line in column f or less. A boundary ends the expression or type being read. none is a floor that no token reaches: only the end of the input is a boundary for it.

Where boundaries are checked. The parser looks for a boundary only at these points, written CONT<f> in the grammar:

  • in an expression, before a binary operator, before a function argument (including a negative argument such as -1 in f -1) and before a field access .field;
  • in a type, before each argument of a type application;
  • in a custom type, before each argument type of a constructor.

Everything else is read at any column: the first token of an expression; the keywords then, else, of and in; the symbols ->, =, :, |, , and the closing brackets; every token of a pattern; and the module header, imports and exposing lists.

Blocks. Three places start a block whose items align at one column c:

BlockColumn cItemsThe block ends
The module1declarationsat the end of the input
letthe column of the first token after letdeclarationsat in, in any column
casethe column of the first token after ofbranchesat a token not in column c, or at in, else or the end of the input
  • Each item starts in column c. After an item, the next token must end the block or be in column c. Otherwise it is:
    • after a value declaration, ELCI1002: Unexpected token after declaration;
    • after a type, a type alias or a destructuring, ELCI1002: Declarations must align at column c.
  • A declaration’s expressions and types have the floor c. A branch’s body has the floor c too. So a line that continues a declaration or branch must be indented past c.

Floors elsewhere.

  • The parts of if, the body of a lambda, the body after in and the scrutinee of case keep the floor of the expression they are in.
  • Inside ( ), [ ] and { } in an expression, and inside a record type, the floor is none. A let or case inside brackets still has its own block column.
  • Inside ( ) in a type, the floor is kept.

This module shows the rules:

sum and doubled align in column 9. first :: _ aligns with [] in column 9, and + first continues the branch because column 17 is past 9. in ends the let block at any column.

Syntactic grammar

Section titled “Syntactic grammar”

Modules and imports

Section titled “Modules and imports”
  • There are no port module or effect module headers.
  • An exposing list names values, types, and types with all their constructors (Shape(..)). It cannot list constructors one by one or name an operator.
  • Imports come before the first declaration.

Declarations

Section titled “Declarations”
  • A signature must be followed directly by the definition of the same name, in the same column. When another value declaration follows instead, it is ELCI1002: A signature must precede its matching definition. When the input ends, or a type or an uppercase name follows, it is ELCI1002: Expected name or Expected lowercase name. Every top-level value needs a signature, but that is a type-checking rule (ELCI2004).
  • A function’s parameters and a destructuring pattern must be irrefutable: _, a name, (), a tuple of irrefutable patterns, a record pattern, or an irrefutable pattern with as. Otherwise: ELCI1002: Function parameters require irrefutable patterns; use case for refutable matching, and likewise for lambda parameters, and ELCI1002: Local destructuring requires an irrefutable tuple or record pattern.
  • Destructuring is only for let. At the top level it is ELCI1002: Top-level declarations require a name.
  • A record type alias also declares a constructor function, with the fields in declaration order.

Types

Section titled “Types”
  • -> groups to the right: a -> b -> c is a -> (b -> c).
  • A lowercase name is a type variable. comparable, appendable and compappend (and names that start with them) are constrained, as in Elm.
  • Tuples are written ( a, b ) or ( a, b, c ); a longer tuple is ELCI2012: Tuples require two or three elements. () is the unit type. Tuple and Unit are not type names: ELCI2012: Write tuple types as ( a, b ) or ( a, b, c ) and ELCI2012: Write the unit type as ().
  • Records are closed. { r | field : Int } is ELCI1002: Extensible records are unsupported; use a closed record.
  • Float is ELCI2001: Float is unsupported; use scaled Int.

Expressions

Section titled “Expressions”
  • if needs its else.
  • if, let and a lambda extend as far to the right as they can: if a then b else c |> f is if a then b else (c |> f). A case ends where its block ends, so an operator on a line left of its branches applies to the whole case.
  • A - after an operand is either BinaryOperator or the start of a NegativeArgument; the characters around it decide (see Adjacency rules).
  • A tuple has two or three elements: ELCI1002: Tuples have two or three elements.
  • (op) is the operator as a function of two arguments, for every operator in the table: (+), (::), (|>). (/) is rejected, like /.
  • { r | x = 1 } updates the record r, which must be a plain lowercase name.
  • .field is the function \r -> r.field.
  • An argument can’t start with if, let, case, \ or -; put it in parentheses. A minus written as in f -1 is the exception: see Adjacency rules.

Patterns

Section titled “Patterns”
  • True and False take no arguments: True x -> is ELCI1002: Expected '->', found 'x'.
  • :: groups to the right: a :: b :: rest.
  • as names the pattern just before it. In first :: rest as all, all names rest, not the whole list (Elm names the whole list); write (first :: rest) as all for that.
  • A tuple pattern has two or three elements: ELCI1002: Tuple patterns have two or three elements.
  • [ a, b ] is the pattern a :: b :: [].
  • Function and lambda parameters and let destructuring take a single PatternAtom, which must be irrefutable (see Declarations).

Operators

Section titled “Operators”

From the tightest binding to the loosest:

PrecedenceOperatorsAssociativity
record.field
10function application f xleft

  • The precedences are those of Elm 0.19, and of Parser.PRECEDENCE. Negation has no number in the parser: it reads its operand at precedence 9, so it covers applications and >>/<< chains and stops before ^. -x ^ 2 is (-x) ^ 2, -f x is -(f x) and 2 * -3 is 2 * (-3).
  • Comparisons do not chain: a < b < c is ELCI1002: Comparison operators cannot be chained; use && or explicit parentheses.
  • Operators of one precedence that associate in opposite directions do not mix: f <| x |> g is ELCI1002: Mixing (<|) and (|>) needs parentheses: they associate in opposite directions, as in Elm, and the same holds for >> and <<.
  • / is ELCI2001: Float division is unsupported; use // for integer quotient, and (/) is ELCI2001: Float division is unsupported; use (//) for integer quotient. % does not exist: use modBy or remainderBy.

Adjacency rules

Section titled “Adjacency rules”

Some tokens mean different things depending on whether they touch: two tokens touch when no character, space or comment, separates them.

Field access and accessors. A . that touches the token before it reads a field of that value. A . that does not touch the token before it, followed by a lowercase name that touches the ., is an accessor function.

SourceMeaning
r.fieldthe field field of r
r .fieldr applied to the accessor .field
List.map .amount orders.amount is \o -> o.amount
(f x).amount, "text".lengtha field of a parenthesized expression, or of a literal
r{- note -}.fieldr applied to .field: the comment separates them

Qualified names. In an expression, a qualified name is written without spaces and ends at its first lowercase part. Every . in it touches the names on both sides.

SourceMeaning
List.mapthe value map of the module List
Maybe.Justthe constructor Just of the module Maybe
Config.settings.feethe field fee of the value Config.settings
List . mapan error: List followed by a stray .

In module names, imports, types and patterns, the parser accepts spaces around the ., but no formatter writes them.

Negative arguments. A - after an operand is read by the characters around it, as in Elm 0.19:

  • It negates the operand that follows when the character before it is whitespace (or (, [, {, ,, or the start of the file) and the character after it is neither whitespace nor -. The negated operand is then an argument of the function before it.
  • Otherwise it subtracts.
  • A - where an expression starts always negates, with or without a space after it.

Parser details that differ from Elm

Section titled “Parser details that differ from Elm”

The parser accepts some programs that Elm rejects, and in one case reads a program differently. These are the details as implemented; formatted code does not rely on them.

  • as in a cons pattern names only the tail: see Patterns.
  • - where an expression starts negates even with a space after it: - 1 is -1.
  • The first token of an expression, and every token taken by keyword (then, else, of, in, ->, =, :, |), may be in any column. So main = followed by 1 in column 1 is accepted, and a signature may continue on a line that starts with -> in column 1.
  • A case branch whose body starts in the branch column is accepted: the body’s first token is not checked.
  • A field access may have spaces after the dot: r. field is r.field.
  • let may declare types (type alias and type). They belong to the module, not the let: a top-level signature can use them. A let with no declarations (let in x) is accepted.
  • The module header and imports are not checked for layout, and the header may be indented.
  • An empty exposing list, exposing (), is accepted, and so is (..) after a lowercase name, as in exposing (main(..)). Neither exposes anything.
  • if, case and let are not reserved: they can name a declaration or a parameter, which then can’t be used. Reserved words can name pattern variables, as in \of -> 1.
  • _ is accepted as a type parameter (type alias Box _ = Int), a record field ({ _ = 1 }) and an as name.
  • A name may start with _, as in _count. It can’t be declared (ELCI1002: Top-level declarations require a name), and in a pattern it reads as a constructor (ELCI2001: Unknown constructor _count in this pattern).
  • Digits are Unicode decimal digits: ١٢ is 12.
