Core modules

This page lists every function the compiler provides without configuration: the Basics prelude, the List, Maybe, Result, Tuple and String modules that every module imports, and the Dict, Map, Array, Value, Interval, Tx, Bytes, Julc.Data and Debug modules. Signatures are exact; the notes describe behavior, failure cases and cost. Names, argument orders and edge cases follow Elm 0.19’s core library; the few differences are listed at the end.

Default imports

Section titled “Default imports”

As in Elm, every source and test module starts with these imports, which you don’t write:

So max, compare, Just and Ok work unqualified, and List.map, String.fromInt and Debug.trace work qualified. Writing one of these imports yourself is allowed; an exposing list then adds names, as in import List exposing (head).

Bytes, Dict, Map, Array, Value, Interval, Tx and Julc.Data need an explicit import, as Dict and Array do in Elm. Using one without it names the import to add:

Name precedence follows Elm, with one addition:

  • A module’s own declarations shadow every import. If your module defines max, it uses its own; Basics.max still reaches the prelude’s.

  • Two imports that expose different things under one name make that name ambiguous. The error is reported where you use the name, and lists the qualified alternatives. A default import counts, so an import Utils exposing (..) whose max differs from Basics.max gives:

  • Addition: a name you list explicitly, as in import Utils exposing (max), takes precedence over a default import.

  • Qualified names always work: Basics.max, Maybe.withDefault, Result.Ok.

  • An import can’t use a default module’s name as its alias. import Utils as String gives ELCI2104: The alias String names a core module that every module imports; choose another alias for Utils.

  • Nor can it use the name of any other core module or of a module in the project, since the two modules’ names would merge. import Julc.Interval as Interval gives ELCI2104: The alias Interval names Elci's core module Interval; choose another alias for Julc.Interval.

The core modules are compiled with your code. A function you don’t use is never compiled into the script, so the default imports cost nothing.

Tuples of two or three elements, closed records and your own custom types complete the picture; see the language reference. Dict, Map and Array are type names you can use without importing their modules. You may also write them as in Elm, with import Dict exposing (Dict) or qualified as Dict.Dict, and likewise for Map and Array. The compiler’s own modules qualify their types the same way: Bytes.Bytes after import Bytes, and Data.Data after import Julc.Data as Data. Value is not an Elm type, so its name needs an import: import Value exposing (Value), or Value.Value after import Value. Reading out.value needs no import. The same holds for Interval: name it after import Interval exposing (Interval), but read ctx.txInfo.validRange without one.

Maybe, Just and Nothing are built into the compiler. A module can’t declare constructors named Just, Nothing, True or False (ELCI2011: Nothing is a constructor of the built-in Maybe type; choose another name), or types named Int, Bool, String, Bytes, Data, List, Maybe, Dict, Map, Array or Float (ELCI2011: Bytes is a built-in type; choose another name).

Comparable types

Section titled “Comparable types”

<, <=, >, >=, compare, min, max, List.sort, List.sortBy, List.maximum and List.minimum work on comparable types. Both operands have the same type.

TypeOrder
Intnumeric
Stringby its UTF-8 bytes, which is Unicode code point order: "Zebra" < "apple"
Byteslexicographic by unsigned byte; a proper prefix comes first
ledger byte strings: PubKeyHash, ScriptHash, PolicyId, TokenName, TxId, DatumHash and the other hashesas Bytes
lists of a comparable typelexicographic; a proper prefix comes first
tuples of comparable typescomponent by component

Bool, (), records, custom types, Maybe, Result, Dict, Map, Array, Value, Data, functions and ledger records such as TxOutRef are not comparable. Sort them by a comparable key with List.sortBy, or with your own order and List.sortWith. Every order is total and agrees with ==: compare x y == EQ exactly when x == y. The arithmetic operators remain Int-only.

The error names the operation and the part of the type that isn’t comparable:

A generic function that compares its arguments names its type variable comparable, as in Elm; see constrained type variables. The keys of a Dict are comparable too.

Semantics:

  • foldl combines from the first element and foldr from the last. Both callbacks receive the element first and the accumulator second: List.foldl (\v acc -> acc * 10 + v) 0 [ 1, 2, 3 ] is 123, and the same with foldr is 321.
  • all stops at the first False and any at the first True.
  • map2 and map3 drop the extra elements of longer lists, as in Elm. On-chain, check lengths first when extras matter: pairing outputs with expected payouts would silently ignore an extra output.
  • The sorts are stable merge sorts, O(n log n): equal elements keep their order. sortBy computes the key at each comparison, so keep keys cheap.
  • Every other function is a traversal, O(n) in the list’s length.

Records and custom types are not comparable. Sort them by a key, or with a comparison:

The constructors [] and ::, list literals [ 1, 2 ], ++ and list patterns are part of the language. Sorting on-chain is not cheap; see costs and performance.

Maybe

Section titled “Maybe”

Maybe a is built in. Every module imports the Maybe module with exposing (Maybe(..)), so Just and Nothing need no qualifier.

Arguments are evaluated before a call, as in Elm, so Maybe.withDefault default m always evaluates default, even when m is a Just. On-chain that costs budget, and a failing default fails the script. Keep an expensive or failing default in a case branch.

Nothing is constructor 0 and Just is constructor 1 in Plutus Data.

In Plutus Data, Ok is constructor 0 and Err is constructor 1, following the declaration order. This is the reverse of PlutusTx’s Either (Left 0, Right 1): a datum written as an Either does not read as a Result, because decoding would swap success and failure.

Dict

Section titled “Dict”

import Dict exposing (Dict). A Dict k v is Elm’s dictionary, with Elm’s functions, argument orders and results. It is stored as a Plutus map whose keys are strictly ascending in the comparable order, so every dictionary has exactly one representation. Keys are comparable types: Int, String, Bytes, ledger hashes such as PubKeyHash, and lists and tuples of these. Values may be any type with a Data encoding.

The bindings come out in key order, whatever order they went in, and the second "apple" replaced the first. Combining two dictionaries follows Elm too. merge folds over both in ascending key order, with one step for keys only in the left dictionary, one for keys in both and one for keys only in the right:

Equality. == compares bindings: two dictionaries are equal when they have the same keys with equal values, however they were built. The values need equality themselves, so a Dict Int (Map Int Int) can’t be compared (ELCI2003). Dictionaries are not comparable.

Cost. A Dict is a list of pairs, not a tree as in Elm:

  • get, member, insert, remove and update walk from the smallest key and stop at the first key that isn’t smaller than the one they look for. They are O(n), at about 1.1 million CPU units per key passed. Small keys are found fastest, and a missing key costs half a scan on average.
  • fromList is a stable merge sort: O(n log n), and O(n) when the pairs are already in key order. For 50 entries it cost about 0.28 billion CPU units with sorted input and 0.66 billion with shuffled input, against 1.5 billion for Map.fromList.
  • size, keys, values, toList, the folds, map, filter and partition are single passes. union, intersect, diff and merge walk both dictionaries once: O(n + m).

In Data. A Dict encodes as a Plutus map with its keys in ascending order. Decoding checks the order: a map whose keys are not strictly ascending, because they are out of order or repeated, fails to decode. The check applies to datums, redeemers, parameters, Julc.Data.decode and property-test arguments, and to every Dict inside them: in records, tuples, custom types, Maybe, Result, Julc optionals, lists and map values. It costs about 1.1 million CPU units per entry. Without it, a datum could place a key after a larger one, where member and get stop before reaching it; datums and redeemers shows the attack. elci apply rejects such a parameter:

Two rules keep every decoded Dict checked. Checking the order needs comparable keys, so a Dict with other keys can’t be decoded from Data:

And a Java library’s generic function can’t be used at a type that contains a Dict, because the library could build one without the check:

Dict or Map? Use a Dict for data you build or look up by a comparable key, including datums. Use a Map for the ledger’s own maps, such as txInfo.withdrawals and txInfo.redeemers, and for keys that are not comparable.

Map

Section titled “Map”

import Map. A Map k v is the ledger’s map representation: a list of key/value pairs, compared by the keys’ Data encoding. The transaction’s maps, such as txInfo.withdrawals, txInfo.redeemers and txInfo.datums, are Maps. Keys and values may be any type with a Data encoding, including records, custom types and ledger types; keys need not be comparable.

Map order. insert puts the binding at the front, and a replaced key moves to the front. So Map.keys (Map.fromList [ ( 1, 10 ), ( 2, 20 ), ( 3, 30 ) ]) is [ 3, 2, 1 ]. filter and map keep the order of the map they are given:

Avoid making results depend on map order. To process the bindings in key order, sort them, List.sortBy Tuple.first (Map.toList prices), or keep them in a Dict.

No equality. == on maps is rejected (ELCI2003): two maps with the same bindings may hold them in different orders. For the same reason Data.encode of two such maps may differ. Compare the lookups you care about, or their toList after sorting, or use a Dict.

Repeated keys. A map built in Elci never repeats a key, but a map decoded from Data can, because decoding doesn’t check a Map’s keys. In such a map, get returns the first binding of the key, remove and insert remove every binding of it, and map and filter keep every binding.

Cost. get, member, insert, remove and update scan the pairs from the front: O(n), at about 1.1 million CPU units per key passed. size, keys, values, toList, the folds, filter and map are single passes. fromList checks each key against the pairs before it, so it is O(n²): building a 50-entry map cost about 1.5 billion CPU units. With comparable keys, Dict.fromList is much cheaper. See costs and performance.

A map or dictionary whose key and value types nothing determines can’t be compiled, because the operations are specialized for them. Map.size Map.empty on its own fails at the call:

Give the map a type, for example with a local definition noPrices : Map String Int.

slice counts a negative index from the end and clamps to the array. For [ 10, 20, 30, 40, 50 ], slice 1 3 is [ 20, 30 ], slice 0 -1 is [ 10, 20, 30, 40 ] and slice -2 10 is [ 40, 50 ].

Arrays are immutable and there is no set or push. Build a list, then convert it once.

No Data encoding. An array cannot be a datum, redeemer, parameter or property-test argument, nor a field of a record, custom type, tuple, list or map. Storing one there fails with ELCI2013: Arrays have no Data encoding and cannot be stored in data; keep a List and convert it with Array.fromList, and Julc.Data.encode on an array is rejected with ELCI3003. Keep lists in your data and call Array.fromList in the handler. An [entrypoint] may return an array on its own; elci eval prints it as Array.fromList [40, 50].

Value

Section titled “Value”

A Value is the ledger’s multi-asset value: an amount of lovelace and quantities of native tokens. out.value and ctx.txInfo.mint are Values, and so is everything this module builds. elci eval prints a value as the Value.fromList that builds it, one ( policy, token name, quantity ) per token; #(empty) is ada’s policy and token name. The two coin entries added up to 5.

Canonical form and equality. Every Value is canonical: policies ascend by their bytes, compared as unsigned, token names ascend within each policy, and no quantity is zero. The ledger’s values are canonical, the functions above keep them so, and decoding a Value from Data rejects any other form. So two values are equal exactly when they hold the same quantities, whatever order the tokens were added in: == works on values, and on your records, tuples and lists that contain them. Values are not comparable; compare them with geq and leq.

Negative quantities. A value may hold negative quantities. The transaction’s mint field holds the tokens it burns as negative quantities. geq and leq handle them: geq a b subtracts b from a and checks that no quantity is below zero, so a burn counts as less than none. positive and negative split a mint into what it mints and what it burns:

Value.negate (Value.negative minted) gives the burned amounts as positive quantities.

Failures. A policy id or token name longer than 32 bytes, and a quantity outside the signed 128-bit range, fail the script: evaluation failed: InsertCoin: tokenName too long: 33 bytes (max 32).

In Data. A Value is stored as the ledger stores it, a Plutus map from policy ids to maps from token names to quantities, so Julc.Data.encode of a value costs nothing. Julc.Data.decode accepts only the canonical form. Unsorted or repeated policies or token names fail with UnValueData: currencies not strictly ordered or duplicate, a zero quantity with UnValueData: zero quantity, and a policy without tokens or an id longer than 32 bytes fail too.

Both conversions work on a Value itself. A type that contains one can’t be decoded yet, and a list or tuple of values can’t be encoded either (ELCI3003). A Value can’t be a datum, redeemer or parameter yet, nor part of one:

Store a List ( PolicyId, TokenName, Int ) instead, and rebuild the value with Value.fromList.

Cost. lovelaceOf, isZero, policies, tokens and toList read the value’s Data directly, and positive, negative, restrictedTo and withoutLovelace filter it entry by entry, keeping it canonical. The other functions convert it to the protocol’s native value (CIP-153 builtins) and back, which costs about a million CPU units for a value of a few assets; sum converts each value once. These small programs, which include building their values, cost:

ProgramCPU
Value.add of Value.lovelace and Value.singleton3.5 million

Interval

Section titled “Interval”

import Interval. An Interval is the ledger’s time range, such as the transaction’s validity range ctx.txInfo.validRange. Times are POSIX milliseconds. A range has a start, range.from, and an end, range.to. Each bound is NegInf, Finite time or PosInf, and is inclusive or exclusive.

A script can’t read the clock. The ledger accepts a transaction only inside its validity range, so a time check asks where the whole range lies: isEntirelyAfter deadline ctx.txInfo.validRange holds only when the transaction cannot run at or before the deadline.

FunctionTypeBehavior
isEntirelyAfterInt -> Interval -> BoolisEntirelyAfter t range: the range has a finite start, and every time in it is after t
isEntirelyBeforeInt -> Interval -> BoolisEntirelyBefore t range: the range has a finite end, and every time in it is before t
containsInt -> Interval -> Boolcontains t range: t is in the range
startInterval -> Maybe Intthe finite start, or Nothing
endInterval -> Maybe Intthe finite end, or Nothing
afterInt -> Intervalfrom t on, inclusive
beforeInt -> Intervalup to t, inclusive
betweenInt -> Int -> Intervalbetween low high: from low to high, both inclusive
everythingIntervalall time

“After” and “before” are strict: no time in the range may equal t. The checks honor each bound’s inclusiveness. A scenario’s Scenario.validFrom t gives the range an inclusive start, and Scenario.validBefore t an exclusive end, so:

  • isEntirelyAfter deadline holds for a range valid from deadline + 1 on, not from deadline. To accept a transaction valid from the deadline itself, check isEntirelyAfter (deadline - 1).
  • isEntirelyBefore deadline holds for a range valid before deadline: the exclusive end may equal it.

The window starts at 1000, inclusive: it is entirely after 999 but not after 1000, and it contains 1000. It ends at 2000, exclusive: it is entirely before 2000 but not before 1999, and it doesn’t contain 2000.

Unbounded ranges. The two deadline checks never hold on an infinite bound. isEntirelyAfter needs a finite start and isEntirelyBefore a finite end, so a transaction that sets no validity range passes neither check, and Interval.before 5 is not entirely after any time. A PosInf start or a NegInf end, which only an empty range has, fails the check that reads it, as in Aiken’s stdlib v2; Aiken v3 lets such an empty range pass both checks. start and end return Nothing for an infinite bound, never a sentinel time. They return the bound’s time whether or not it is inclusive; read range.from.isInclusive when that matters, or use the checks, which account for it.

The constructors Interval, IntervalBound, Finite, NegInf and PosInf come from Julc.Ledger, as in the example. The Interval type is the ledger’s, so import Julc.Ledger exposing (Interval) names the same type.

Cost. Each check reads one or two bounds and compares integers. isEntirelyAfter and isEntirelyBefore cost about 2.8 million CPU units, contains about 5.5 million.

  • Credentials, not addresses. outputsTo and valuePaidTo match an output’s payment credential (output.address.credential) and ignore its staking part. Whoever builds the transaction chooses the payee’s staking part: a payment to the seller’s key counts whatever staking credential its address carries. When the staking part matters, store the payee’s full Address and compare output.address. continuingOutputs compares whole addresses, staking part included.
  • Payments must be tagged. “Some output pays the seller” is true for two script inputs spent in one transaction when one output pays for both. This is the double-satisfaction attack, and an untagged valuePaidTo check has it. Require each payment to carry the spent output’s reference as its inline datum, as below, or allow one script input per transaction. Reading the transaction explains both defences.
  • Datums stay Data. inlineDatum returns Nothing for an output with a datum hash or no datum. datumOf also finds a datum by its hash in txInfo.datums, and returns Nothing when the transaction doesn’t supply it. Decode a datum with an annotated Data.decode, which fails the script on a malformed datum, or compare it with an expected encoding: == on Data compares structure.
  • Values. valueSpent sums the spent outputs, not the reference inputs. valueProduced sums the outputs; the fee and the minted tokens are separate fields, txInfo.fee and txInfo.mint. mintedOf is Value.tokens policy ctx.txInfo.mint: an empty Dict when the policy mints nothing.

== and /= compare byte strings. <, <=, >, >= and compare order them lexicographically, a proper prefix first, with the Plutus builtins lessThanByteString and lessThanEqualsByteString. Ledger hashes such as PubKeyHash are distinct types that compare and order like bytes; read their bytes with .hash.

Julc.Data

Section titled “Julc.Data”

import Julc.Data as Data. Explicit conversions between Elci values and Plutus Data.

FunctionTypeBehavior
decodeData -> aJulc’s strict decoder for a. Malformed Data fails the script.
encodea -> DataThe Data encoding of a.
fromOptionalJulcOptional a -> Maybe aRe-tags a Julc optional as a Maybe.
toOptionalMaybe a -> JulcOptional aThe reverse.
  • Supported types. Int, Bool, String, Bytes, Data, your records and custom types, tuples, Maybe, Result, Order, lists, dictionaries, maps and optionals of these, a Value, and imported types whose provider approves decoding or encoding (for example PubKeyHash or TxOutRef). The rest are rejected with ELCI3003: (), functions, Array, and ledger types without a checkable layout, such as TxOut for decode. A type that contains a Value can’t be decoded yet.
  • Known types for decoding. decode must know the type it creates where it is used. If inference cannot tell, annotate the binding (local definitions accept signatures). Otherwise the call fails with ELCI3001: Cannot determine the type converted by Julc.Data.decode; add a type annotation. encode and the optional adapters don’t need to know it: Data.encode Nothing is Constr 0.
  • Strict decoding. decode never returns a Maybe for malformed input. A value of the wrong shape, such as an integer where a record is expected, fails with an error like UnConstrData: not ConstrData. A Dict whose keys are not strictly ascending fails too, and so does a Value that is not canonical.
  • Optionals. Julc’s optional tags Some as 0 and None as 1, the reverse of Maybe. The adapters swap the tags without decoding the payload.
  • Equality. == and /= on Data compare structure exactly, with the equalsData builtin. Elci’s encodings are deterministic, so Data.encode a == Data.encode b exactly when a == b for your records, custom types, lists and dictionaries. That makes a datum check one comparison: Tx.inlineDatum output == Just (Data.encode expected). A Map has no ==: two maps with the same bindings may hold them in different orders, so their encodings may differ too. Compare their toList after sorting, or use a Dict. Data is not comparable: < and sorting reject it.

The record and the record literal with the same fields encode alike; Just 5 and 5 do not. The two dictionaries hold the same bindings, so their encodings are equal; the two maps hold them in different orders, so theirs are not.

The encoding rules are in the language reference.
