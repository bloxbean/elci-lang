CLI

This page documents every elci command and option, what each one prints and writes, and how it reports errors. The examples use the native executable; the JVM launcher accepts exactly the same arguments.

Synopsis

Section titled “Synopsis”

elci, elci help, elci --help and --help after any command (such as elci eval --help) print this text and exit with status 0.

The second version is the Julc build the compiler is pinned to. A project’s julc-version in elci.toml must match it exactly.

Common behavior

Section titled “Common behavior”

Project directory. Every command except init and explain takes an optional project directory: the directory that holds elci.toml. It defaults to the current directory. Giving two directories is an error.

Two kinds of project. A project configures either [validators.<name>] tables or one [entrypoint] function. check, build and test work with both; eval needs an [entrypoint]; apply and --validator need validators.

Output streams. Results go to standard output, including test results and a failed eval run. Compile, configuration and command-line errors go to standard error.

Exit status.

StatusMeaning
0The command succeeded.
1Any error: invalid arguments or configuration, a compile error, an eval that failed at run time, a failing test, or no tests found.

Error format. A compile error starts with a line that names the source location and the code. The source line follows, with carets under the reported code, and then any hints. The report ends with the command that explains the code:

The first line always has the form path:line:column: code: message. A problem inside a bundled module such as List is reported where your code uses it, or otherwise as <bundled>/List.elm, without an excerpt. For a validator, the elci.toml table follows the diagnostic, on its own line:

Configuration and command-line errors start with elci: and carry the code ELCI4001, apart from the few listed under errors without a code:

Several errors. A run reports every compile error it finds, in source order and separated by blank lines, followed by a count such as 3 errors. It shows at most 20, then a line such as ... and 3 more. Each top-level declaration reports its first error, and type errors are reported only when there are no syntax, import or qualified-name errors. Code generation, configuration and command-line errors stop the run at the first. The diagnostics page explains how to read them and lists every code.

Colour. On a terminal, compile errors are in colour, unless the NO_COLOR environment variable is set. Every command takes --color=auto, --color=always or --color=never to choose; auto is the default. Any other value is an ELCI4001 error. JSON reports are never coloured.

JSON reports. check, build, eval and test take --report=json. With it, each error is printed on standard error as one JSON object on its own line (JSON Lines), instead of the text above. A run with one error prints one line; a run with several prints one line for each. Here one is formatted with jq:

FieldContents
codeThe ELCI code, or null for an error without one
path, line, columnThe location, or null for an error without one
messageThe message, without the path and code
hintsThe hints, as an array of strings; empty when there are none
excerptThe source lines and their caret lines, separated by newlines, or null
contextThe elci.toml line and table of a failing validator, such as my-project/elci.toml:6: [validators.main], or null

The JSON report has no count line and no elci explain line. A configuration or command-line error keeps the same fields, with null location fields:

The exit status doesn’t change. Results stay text on standard output: the check and build lines, the value, budget or evaluation failed: line of eval, and test results, including failing tests. init, apply and explain reject the option:

elci init

Section titled “elci init”

Creates a new project in an empty or missing directory.

OptionDefaultMeaning
--purposespendThe first handler’s purpose: spend, mint, withdraw, certify, vote or propose. function creates an [entrypoint] project for elci eval instead.
--validatormainThe validator’s name: lowercase letters, digits, - or _, starting with a letter. Not allowed with --purpose function.

A validator project gets elci.toml, src/Main.elm, tests/MainTest.elm, README.md and a .gitignore that ignores build/. The starter handler accepts transactions signed by an owner deployment parameter, and the two tests check that the owner passes and anyone else is rejected. A --purpose function project gets elci.toml, src/Main.elm (returning 42), README.md and .gitignore, and no tests.

Errors are ELCI4001, such as ELCI4001: Project directory is not empty: ..., ELCI4001: Unsupported purpose: lend; expected spend, mint, withdraw, certify, vote, propose or function and ELCI4001: Invalid validator name '9bad'; use lowercase letters, digits, '-' or '_', starting with a letter.

elci check

Section titled “elci check”

Compiles the project and reports each result without writing files.

OptionMeaning
--validator <name>Check only this validator. Repeat it to select several. Validator projects only.
--report=jsonPrint each error as one JSON object on its own line on standard error (see JSON reports).

For a validator project, it prints one line per validator, sorted by name, with the purposes it handles and its size in FLAT bytes:

For an [entrypoint] project it prints the function instead:

check compiles the source directories only; test modules are compiled by elci test. When expected-abi is set, check also compares the ABI and fails on drift, exactly like build.

elci build

Section titled “elci build”

Compiles the project and writes its artifacts under build/. It prints the same lines as check.

It takes the same options as check.

For each validator it writes build/validators/<name>/:

FileContents
validator.flatthe script’s FLAT bytes
validator.plutusa PlutusScriptV3 text envelope with the CBOR hex
validator.plutus.jsonJulc’s artifact: type, purpose, CBOR hex, script hash, parameters and sizeBytes
abi.jsonElci’s ABI manifest: handlers, datum and redeemer schemas, parameters

build/validators/elci-outputs.json records which files Elci owns. The hash in validator.plutus.json is empty for a validator with parameters, because applying parameters changes the hash. Its purpose is multi when the validator has several handlers.

Publishing is all-or-nothing: every selected validator is compiled and ABI-checked before any file is written, and files are replaced atomically. A build of all validators also removes the output directories of validators you deleted from elci.toml. A build with --validator touches only the selected validators. Rebuilding a validator removes the applied.plutus.json that elci apply left in its directory, since it belonged to the previous script.

An [entrypoint] project writes build/validator.flat, build/validator.plutus and build/abi.json.

See build and deploy for using these files.

elci eval

Section titled “elci eval”

Runs an [entrypoint] project’s function on Julc’s evaluator and prints the result.

OptionMeaning
--builtinsAlso print the builtin calls of the run, one per line, with arguments and result. The log keeps the last 20 calls.
--report=jsonPrint each compile error, or a configuration error, as one JSON object on its own line. A failed evaluation still prints evaluation failed: as text.

The first line is the value, written in Elci syntax. The second is the CPU and memory consumed. Each Debug.trace message follows on its own line:

Values print as you would write them: True, "text", [1, -2], Just 5, ( 1, "a" ), records with their fields in name order, byte strings as #474f4c44 (and #(empty)), maps as Map.fromList [...], dictionaries as Dict.fromList [...], arrays as Array.fromList [...] and values as Value.fromList [( #policy, #token, quantity )], where ada’s policy and token name are #(empty). eval passes no arguments, so an entrypoint of function type prints <function>. If evaluation fails, it prints evaluation failed: with the reason, then the budget, and exits with status 1:

eval rejects validator projects and the --validator option; test validators with elci test.

elci test

Section titled “elci test”

Runs the tests in the project’s test directories (tests/ by default) and reports each with its budget.

OptionDefaultMeaning
--match <substring>all testsRun tests whose full name (Module.test) contains the substring, ignoring case.
--seed <n>randomSeed for property tests. The seed used is printed, so any run can be repeated.
--fuzz <runs>100Number of runs for each property test. Must be positive.
--report=jsontextPrint each compile error, such as one in a test module, or a configuration error as one JSON object on its own line. Test results stay text.

A failing test prints its details and traces, indented, and the command exits with status 1:

The (seed ...) suffix appears only when a property test ran. If nothing runs, elci test prints No tests found in tests or No tests match '<substring>' and exits with status 1, so it is safe as a CI gate. What counts as a test is described in unit tests.

elci apply

Section titled “elci apply”

Applies deployment parameters to a validator and writes the applied script.

OptionMeaning
--validator <name>Required. Exactly one validator.
--param <name>=<value>Required once for every name in the validator’s parameters, and only for those.
--output <file>Where to write the applied script. Default: build/validators/<name>/applied.plutus.json.

Each value is Plutus Data in the detailed JSON schema that cardano-cli uses:

JSONData
{"int": 5}integer
{"bytes": "a2c2..."}byte string, in hex
{"list": [ ... ]}list
{"map": [{"k": ..., "v": ...}]}map
{"constructor": 0, "fields": [ ... ]}constructor

Write @path instead of JSON to read the value from a file. That path is relative to the project directory, while --output is relative to the current directory. JSON strings may not contain escapes.

apply compiles the validator, checks its ABI when expected-abi is set, and checks every value off-chain with the strict decoder for the parameter’s type, because the script itself does not validate parameters. A value of the wrong shape is rejected before anything is written:

Other errors name the problem: missing --param owner=<plutus-data-json>, parameter owner is given more than once, validator main has no parameter 'nope'; declared: owner, and validator main declares no parameters. See parameterized validators.

elci explain

Section titled “elci explain”

Prints the long-form entry for a diagnostic code.

The code may be written ELCI2002, elci2002 or 2002. An entry says what the code means and its common causes, shows a failing example with its exact output, and gives the fix and the pages to read. Code blocks are indented by four spaces. Without a code, explain lists every code with its title:

The list goes on with every other code. An unknown code, or more than one, is an error:

The entries are part of the compiler, so they match its version. The diagnostics page shows a whole entry.
