Diagnostics

Elci reports each error with a stable code and a source location, shows the source code it is about and suggests a fix. This page explains how to read a diagnostic, how a run reports several errors, and how tools can read them. It then lists every code, and shows the most common errors with a small program that triggers each one, the exact output and the fix.

Reading a diagnostic

Section titled “Reading a diagnostic”

A compile error starts with one line, path:line:column: code: message. A blank line follows, then the source line with carets under what the error is about, then any hints:

  • The first line has the same form for every error, so editors and scripts can parse it. The path is the file of the module where the problem is, which may be a module imported by the one you compiled. A problem inside a bundled module such as List is reported where your code uses it, or otherwise as <bundled>/List.elm.
  • The code names the class of error and never changes between releases. The message says what is wrong in terms of your code: which argument, branch, list element, operator side, annotation or field has the wrong type, or which patterns a case doesn’t cover.
  • The excerpt shows the line with its number, and underlines what the error is about. For an error at the end of the file, it points just past the last code. An error in a bundled module has no excerpt.
  • Each hint suggests a likely fix: a close name, a conversion such as String.fromInt, or an import to add. An error has zero or more hints.
  • The last line names the codes of the run and the command that explains them; see elci explain. The examples in the rest of this page leave it out and show only the diagnostic. Some show only its first line, without the excerpt and hints.

Types in messages are written as in source, in backticks: Result a Int, Order. When two types of one name meet in a message, both are qualified, as in Main.Value and Julc.Ledger.Value.

For a validator, the elci.toml table follows the diagnostic, on its own line:

Every error makes the command exit with status 1. Codes starting with ELCI1 come from the lexer and parser, ELCI20 from type checking, ELCI21 from modules and imports, ELCI3 from code generation and ELCI4 from configuration and the backend.

What is underlined

Section titled “What is underlined”

The carets underline the reported token, such as a name, a qualified name or a string literal with its quotes. When the error is about a whole expression, they underline all of it. This is the case for an argument, a list element, the body of a case branch and a field access such as .price:

An expression over several lines is underlined on each of its lines, up to five:

The line and column of the first line are where the underline starts. A longer expression shows its first five lines, then a line with ….

Some expressions are reported at a token inside them: an operation such as "x" ++ "y" at its operator, and a call without parentheses such as String.fromInt 3 at its last argument. The caret then marks that token alone, as an underline from there would cover only part of the expression.

Colour

Section titled “Colour”

On a terminal, the path and code, the carets and Hint: are in colour. Output to a file or a pipe is plain, and so is any output when the NO_COLOR environment variable is set. --color overrides this on any command:

OptionColour
--color=autoOn a terminal, unless NO_COLOR is set. The default.
--color=alwaysAlways, also in a pipe.
--color=neverNever.

The text is the same, character for character, with and without colour. The JSON report is never coloured.

Several errors in one run

Section titled “Several errors in one run”

A run reports every error it finds, not just the first. Compilation has three phases: lexing and parsing, name resolution, and type checking. Each phase reports all of its errors. A later phase runs only when the earlier ones found none, as in Elm, so one mistake isn’t reported again as a different error later.

  • Order. Errors are shown in source order: by module, then by line and column. A blank line separates them.
  • Count. When there is more than one error, a line such as 3 errors follows them.
  • Limit. A run shows at most 20 errors, then a line such as ... and 3 more. The count still gives the total.
  • One per declaration. Each top-level declaration reports its first error. A declaration whose definition fails still has the type its annotation gives it, so its callers are checked against the annotation and don’t report errors of their own. Above, main passes fee to total, which needs an Int. The annotation says fee is one, so main is not reported.
  • Once each. A mistake that fails several checks alike, such as each comparison inside List.sort, is reported once.
  • Phases. A module with a syntax error is not type-checked. Nor is a program with an import or qualified-name error (ELCI21xx), such as Lsit.length. Fix those, and the next run reports the type errors. An unknown unqualified name (ELCI2005), as above, is found while type checking and is reported with the type errors.
  • One at a time. Code generation (ELCI3xxx), configuration and command-line errors (ELCI4xxx) still stop the run at the first error.

ELCI2003: unsupported equality, ordering or append

Section titled “ELCI2003: unsupported equality, ordering or append”

Equality is rejected for functions, Map, Array and imported types without approved equality, such as TxOut. A Dict has equality when its values do, and a Value and Data always have it. When the offending type is inside another, the message names it: The operator == cannot compare List (Int -> Int) values: Int -> Int is part of them, and functions have no equality. ++ needs a String or a List: 1 ++ 2 gives ELCI2003: The operator ++ appends String or List values, not Int.

Fix: compare the values you care about, such as a map’s lookups or a decoded datum, or keep keyed data in a Dict, which has equality.

Ordering (<, compare, max, List.sort and the rest) needs a comparable type. The message names the operation and the part of the type that isn’t comparable:

For records and custom types, the message goes on to suggest a key:

Fix: compare a comparable field, or sort with List.sortBy (\person -> person.age) or List.sortWith.

A signature whose type variable is compared or appended must say so with its name, as in Elm (constrained type variables):

Fix: write larger : comparable -> comparable -> comparable. For ++, the message suggests appendable. A caller that then passes the wrong type is reported at the call: ELCI2003: `twice` appends String or List values, not Int. Elm’s number has its own message:

Decoding a Dict checks that its keys are in order, so a Dict in a datum, a redeemer, a parameter or a Julc.Data.decode result needs comparable keys:

Fix: use a Map, whose keys may be any type with a Data encoding.

ELCI2004: missing signature

Section titled “ELCI2004: missing signature”

Fix: add double : Int -> Int directly above the definition. Local definitions do not need one.

ELCI2005: unknown name

Section titled “ELCI2005: unknown name”

Fix: correct the spelling, or import the module that defines the name. The hint lists up to three close names. It looks first at the names the module can write unqualified, local ones included, and then at qualified names. A name is close when it differs only in case, by one edit for a name of three to five characters, or by two edits for a longer name. Swapping two neighbouring letters counts as one edit.

A name that an imported module exposes, but that its import doesn’t list, gets a hint that says how to reach it. Here the module Helper exposes double:

A name that a Java library module doesn’t export is reported with a reminder to check its exports:

A qualified name whose module is missing, not imported or lacks the name is ELCI2104; see module and import errors.

ELCI2006: duplicate binder or unreachable pattern

Section titled “ELCI2006: duplicate binder or unreachable pattern”

Fix: remove the branch that can never match. A pattern that binds the same name twice, such as ( x, x ), gives ELCI2006: Duplicate pattern variable x.

ELCI2007: non-exhaustive case

Section titled “ELCI2007: non-exhaustive case”

Fix: add a Cancel -> branch. Prefer naming every constructor over _ ->, so that adding a constructor later points you to every case to update.

The message lists the missing patterns as you would write them, including nested ones:

The list is complete: a branch for each pattern in it makes the case exhaustive. It shows up to three patterns, then how many more there are, as in it is missing `Square _`, `Triangle _ _ _`, `Line` and 1 more. Lists and literals are covered too: a case on a list with branches for [] and [ _ ] is missing _ :: _ :: _, and one on an Int or a String without a _ branch is missing _.

ELCI2008: eager value cycle

Section titled “ELCI2008: eager value cycle”

Fix: values are computed eagerly, so they cannot depend on each other in a loop. Break the cycle, or turn the recursion into a function.

ELCI2009: type is not concrete

Section titled “ELCI2009: type is not concrete”

A validator handler gets Handler Main.mint requires a concrete type, and a property test with generic arguments gets a similar message. Fix: replace the type variable with a concrete type, such as List Int.

ELCI2010: unknown record field

Section titled “ELCI2010: unknown record field”

Fix: use one of the listed fields. A field name close to one of them, such as order.amont, also gets the hint did you mean `amount`?. When Elci cannot tell which record a field access belongs to, add a signature with the record type.

Section titled “ELCI3001: type is not known where it is used”

List.length works on any list, so nothing tells Elci what the decoded list contains, and it cannot pick a decoder. Fix: give the value a type:

A generic Java library function needs its type arguments. When a core module such as Map uses one at a type nothing in your program determines, the error is reported at your call:

ELCI3002: specialization limit

Section titled “ELCI3002: specialization limit”

A program may create at most 256 specializations of its generic functions. This happens with polymorphic recursion that inference did not already reject. Fix: make the recursive function monomorphic.

ELCI3003: no Data encoding

Section titled “ELCI3003: no Data encoding”

Generic Java methods and Julc.Data conversions need a type with a Data encoding:

Fix: use a Data-encodable type. Functions, () and Array have no encoding, and TxOut can’t be decoded. A Value converts on its own, but a type that contains one can’t be decoded yet, and a list or tuple of values can’t be encoded: convert them with Value.toList and back with Value.fromList.

A Java library’s generic function can’t be used at a type that contains a Dict. The library could build the dictionary itself and skip the check that its keys are in order:

Fix: pass the library a Map or a List, and build the Dict with Dict.fromList. A type that holds a Value is rejected the same way:

Use the core List and Value modules instead.

ELCI4002 and ELCI4003: backend

Section titled “ELCI4002 and ELCI4003: backend”

ELCI4002 means Julc’s PIR verifier rejected the code Elci generated. It is reported at the Elci declaration involved and keeps Julc’s own JULC00xx code in the message. ELCI4003 means the Julc backend in use lacks a capability the program needs, which happens only with a mismatched Julc build. Both point at a compiler problem rather than a mistake in your code: please report them with the program that triggers them.
